# Готовые образы и публикация

[К содержанию](README.md)

Есть два независимых способа запуска:

- `deploy/compose.local.yaml` — локальная разработка: собирает семь собственных образов из исходников.
- `deploy/compose.yaml` — установка готовых образов: не содержит `build` и не требует checkout.

В checkout запускай Compose из корня репозитория с `--project-directory .`:
`docker compose --project-directory . -f deploy/compose.local.yaml up -d --build` для разработки
или `docker compose --project-directory . -f deploy/compose.yaml up -d` для готовых образов.
Так `.env`, контекст сборки и `container_data/` остаются в корне репозитория.

Оба варианта используют одинаковые сервисы, настройки, каталоги данных и локальные порты.
Их соответствие проверяет `python3 tools/checks/check-compose.py`. Не запускай оба варианта
одновременно с одним Telegram-токеном или общими каталогами данных.

## Какие образы собираем

- **`openalbert`** — Go-приложение, инспектор и Chromium из Alpine.
- **`computer`** — Ubuntu 24.04, SSH, Python, Git и пользователь `albert` с `sudo` без пароля.
  Этот же образ запускает одноразовый `computer-init` для создания ключей.
- **`backup`** — отдельный контроллер бэкапов с Go-утилитой, Docker CLI и Compose.
  Включается профилем `backup`; расписание и монитор работают внутри контейнера.
- **`stt`** — NeMo-Speech.cpp, наш Go-адаптер, FFmpeg и bootstrap. Веса скачиваются
  при запуске и хранятся отдельно в `container_data/stt`; в образ не включаются.
- **`log-gateway`** — наш приёмник и маршрутизатор Docker-логов.
- **`minio`** — неизменённые исходники MinIO, закреплённые на коммите
  `9e49d5e7a648f00e26f2246f4dc28e6b07f8c84a` (`RELEASE.2025-10-15T17-29-55Z`).
- **`minio-init`** — клиент `mc` из коммита
  `7394ce0dd2a80935aded936b09fa12cbb3cb8096` (`RELEASE.2025-08-13T08-35-41Z`)
  и наш скрипт создания бакета. Скрипт включён в образ и допускает повторный запуск.

Собственные сборки MinIO и `mc` нужны, поскольку прежние публичные образы не
получаются из реестров. Они собираются из исходников без зависимости от этих образов.
Закреплённые исходники доступны по ссылкам в `services/minio/Dockerfile`; лицензии
AGPL и credits клиента включены в соответствующие образы. Это сборки сторонних
компонентов, их обновление нужно сопровождать отдельно. Версия сервера новее
прежнего `RELEASE.2025-04-22T22-12-26Z`: перед переносом существующих данных сделай
резервную копию и проверь обновление на копии хранилища.

**Стандартными оставляем** `postgres:17.9-alpine`, `temporalio/auto-setup:1.29.1`,
`temporalio/ui:2.54.1` и `victoriametrics/victoria-logs:v1.53.0`.
Собственного кода в них нет; SQL и dynamic config передаются средствами Compose,
поэтому отдельные сборки этих сервисов не нужны. Все четыре образа имеют ARM64-варианты.
`auto-setup` соответствует текущей установке с одним сервером Temporal; отказоустойчивый
кластер и отдельный процесс миграций эта конфигурация не настраивает.

## Локальная сборка и публикация

Все проверки и сборки выполняются локально через Task, Docker Buildx Bake и Tart.
Полный каталог команд, установка инструментов и отчёты описаны в
[локальных проверках](local-checks.md).

```sh
task verify
```

Команда проверяет форматирование, Go analysis, Compose, Go race-тесты с временными
PostgreSQL/VictoriaLogs и настоящими Chromium/FFmpeg, документацию, браузерные
сценарии и нативные macOS-тесты в Tart. Затем собирает семь образов для архитектуры
Docker engine, запускает smoke каждого образа и чистое развёртывание с перезапуском.
Telegram/LLM заменены синтетическими API, рабочий `.env` не читается, веса STT не скачиваются.
MinIO проверяется реальным S3-контрактом и повторной инициализацией бакета; Ubuntu —
контрактом SSH, sudo, файлов, отмены и восстановления после пересоздания.

Публикация запускается отдельно, из чистого checkout ветки `master`:

```sh
docker login ghcr.io
OPENALBERT_IMAGE_PREFIX=ghcr.io/mishankov/openalbert task publish
```

`task publish` сам повторяет все проверки и собирает/проверяет **обе** архитектуры
`linux/amd64` и `linux/arm64`, включая чистое развёртывание каждой.
На Apple Silicon AMD64 использует эмуляцию и может собираться значительно дольше.
Образы загружаются только после успешной проверки всех этапов. Авторизация — локальный
Docker credential store; namespace задаётся явно через `OPENALBERT_IMAGE_PREFIX`.

Каждый компонент получает теги `sha-<полный SHA>-amd64` и `sha-<полный SHA>-arm64`,
после чего создаются общие манифесты `sha-<полный SHA>` и `master`:

```text
ghcr.io/<owner>/<repository>/openalbert:sha-<полный SHA>
ghcr.io/<owner>/<repository>/computer:sha-<полный SHA>
ghcr.io/<owner>/<repository>/stt:sha-<полный SHA>
ghcr.io/<owner>/<repository>/log-gateway:sha-<полный SHA>
ghcr.io/<owner>/<repository>/minio:sha-<полный SHA>
ghcr.io/<owner>/<repository>/minio-init:sha-<полный SHA>
```

Для воспроизводимой установки выбирай SHA-тег от полностью успешного локального
прогона. Публикация нескольких пакетов не атомарна: при ошибке повтори `task publish`
из того же коммита и дождись общего успеха. На сервер ничего автоматически не развёртывается.
Проверь видимость каждого GHCR package: для анонимного pull пакет должен быть public;
для закрытых пакетов на сервере нужен `docker login ghcr.io` с правом чтения.
Если в защите ветки остались обязательные проверки удалённых workflows, удали эти
требования в настройках репозитория: локальные команды не создают GitHub status checks.

## Установка без исходников

Нужны Docker Engine, Docker Compose **2.23.1 или новее**, Linux AMD64 или ARM64,
свободные порты и постоянный диск. Inline configs требуют указанной версии Compose.
Для Raspberry Pi выбирай 64-битную ОС и SSD для данных; скорость полного стека,
включая STT и параллельные браузеры, на Pi пока не проверена.

Скачай `deploy/compose.yaml` из выбранного коммита как `compose.yaml`
в каталог установки и положи рядом `.env.release.example` из корня репозитория.
Дальнейшие команды этого раздела выполняются в каталоге установки без исходников:

```sh
cp .env.release.example .env
mkdir -p container_data/knowledge
sudo chown 10001:10001 container_data/knowledge
```

В `.env` укажи `OPENALBERT_IMAGE_PREFIX=ghcr.io/<owner>/<repository>` в нижнем регистре
и `OPENALBERT_IMAGE_TAG=sha-<полный SHA коммита>` либо `master`. Заполни Telegram token,
разрешённые ID, настройки LLM и собственные PostgreSQL/S3 credentials.
`POSTGRES_PASSWORD` должен быть URL-safe: он подставляется в URL подключения.
Например, случайный пароль в hex не требует дополнительного URL-кодирования.
Пустые обязательные значения Compose отвергает до создания контейнеров.

```sh
docker compose config -q
docker compose pull
docker compose up -d
docker compose ps
```

Примеры настроек включают локальный STT через `COMPOSE_PROFILES=local-stt`.
Первый запуск скачивает около 742 МБ весов и прогревает модель. Бот может
запуститься раньше готовности STT; перед голосовыми сообщениями дождись `healthy`.
Для отключения распознавания задай `COMPOSE_PROFILES=` и `STT_BASE_URL=`.
Для внешнего STT оставь `COMPOSE_PROFILES=` и укажи его `STT_BASE_URL`, модель и ключ.
При изменении уже работающей установки останови локальный STT командой
`docker compose --profile local-stt stop stt`, затем выполни `docker compose up -d`.
Одна смена URL не отключает профиль; `--remove-orphans` не останавливает сервисы
из отключённых профилей.

Данные сохраняются в `container_data`: PostgreSQL, MinIO, VictoriaLogs, STT, Markdown-память и компьютер (ключи, домашний
каталог и рабочие файлы). `computer-init` автоматически подготавливает SSH; порт
компьютера доступен только внутри выделенной Compose-сети. Подробности и параметры —
[Ubuntu-компьютер](development.md#ubuntu-компьютер-альберта).
Инициализация баз Temporal выполняется только на пустом PostgreSQL data directory;
при переносе существующей установки нужны все три базы, вложения и память.
Смена `POSTGRES_PASSWORD` в `.env` не меняет пароль уже созданного пользователя БД.
Порты опубликованы только на `127.0.0.1`; удалённый доступ к инспектору и служебным
интерфейсам можно организовать SSH-туннелем. Telegram использует исходящий polling,
проброс входящего порта для бота не нужен.

Например, `ssh -N -L 8080:127.0.0.1:8080 user@server` открывает инспектор на
`http://localhost:8080/inspect/`. Если используешь другой локальный порт, задай
соответствующий `INSPECTOR_PUBLIC_URL`, чтобы ссылки бота вели на доступный адрес.

Для прямого доступа из доверенной LAN замени публикацию порта сервиса `openalbert`
на `"192.168.1.31:8080:8080"`, указав LAN-адрес своего сервера, и пересоздай
приложение: `docker compose up -d --no-deps --force-recreate openalbert`.
`INSPECTOR_PUBLIC_URL=http://192.168.1.31:8080/inspect/` задаёт только адрес ссылок.
Проверок Host/Origin и авторизации в приложении нет; доступ регулируется публикацией
порта в Compose. Подробности — [инспектор](inspector.md).

## Обновление установки

Сделай резервную копию данных, возьми Compose и пример настроек из нужного коммита,
задай общий SHA-тег и выполни:

```sh
docker compose pull
docker compose up -d
```

Не выполняй параллельно `up` из локального Compose. Возврат к старым образам
возможен только с учётом совместимости схемы БД и формата данных MinIO; для
обратного несовместимого изменения нужна соответствующая резервная копия.

## Резервная копия и восстановление

### Автоматические копии в S3

`albert-backup` работает **в отдельном контейнере `backup`** от root, независимо
от приложения и Temporal. В контейнере находятся утилита, расписание и монитор;
на хосте достаточно Docker Compose. Контроллер продолжает работать, пока остальные
сервисы остановлены, и автоматически запускается после перезагрузки Docker.
Для этой схемы нужны стандартные каталоги `container_data`, опубликованные образы
с registry digests и отдельный внешний S3-совместимый бакет. Локальный MinIO
с вложениями остаётся рабочим хранилищем.

Перед остановкой утилита проверяет бакет, пути данных, версии образов и свободное
место. Затем записывает событие начала, выдерживает `notice_seconds` и останавливает
работающие сервисы Compose, кроме самого `backup`. В архив входят:

- PostgreSQL целиком: базы `openalbert`, `temporal`, `temporal_visibility`, WAL и роли;
- каталог MinIO со всеми вложениями и служебными данными;
- `knowledge`: память, `SOUL.md`, `USER.md` и skills;
- `computer`: SSH-ключи, домашний каталог и рабочие файлы встроенного компьютера;
- `.env`, выбранный Compose и манифест точных digest образов.

Логи VictoriaLogs, скачиваемые веса STT, временные архивы, состояние бэкапов
и отдельный каталог `backup-config` не архивируются.
Символические ссылки, внешние tablespaces и изменённые пути данных отклоняются.
Для таких установок сначала нужна отдельная схема резервирования.

Архив сжимается и сразу шифруется [age](https://age-encryption.org/) публичным
X25519-ключом; открытый архив на диске не создаётся. На время локального копирования
Альберт недоступен. Пауза включает остановку и запуск сервисов и зависит от данных
и диска. Во время копирования нельзя редактировать сохраняемые файлы или параллельно
управлять Compose. Перед загрузкой в S3 сервисы запускаются с проверкой готовности.
При ошибке или SIGTERM утилита тоже пытается их запустить. Журнал `resume.json`
позволяет монитору повторить запуск после SIGKILL или перезагрузки; запускаются
только сервисы, работавшие перед бэкапом.

После загрузки утилита полностью читает зашифрованный объект из S3 и сравнивает
размер и SHA-256. Только затем создаётся `complete.json`, и копия считается успешной.
Проверка передачи байтов не заменяет проверку восстановления.

`keep_days` — число **разных дат с успешными копиями** в настроенном часовом поясе.
При 14 сохраняются все копии за последние 14 успешных дат; несколько ручных запусков
за день не вытесняют предыдущие даты. Пропущенные дни и ошибки не учитываются.
Ротация выполняется только после новой проверенной копии.
Оставшиеся после обрыва загрузки объекты без `complete.json` старше 48 часов
удаляются после успешного запуска; незавершённые multipart очищает правило бакета.

Используй отдельный prefix для каждой установки и непубличный внешний бакет
с изначально выключенным versioning. Включённое или suspended versioning
отклоняется, иначе удаление оставляло бы оплачиваемые версии. Аккаунту нужны права
проверки бакета и versioning, перечисления, чтения, записи, удаления объектов
и отмены multipart-загрузок в выделенной области. Не назначай этому prefix
возрастную Lifecycle-ротацию завершённых копий: она удаляла бы их независимо от
числа успешных дней. Отдельное правило удаления незавершённых multipart допустимо.

### Настройка контейнера резервирования

`backup` включается отдельным профилем Compose. Ему передаются:

- каталог установки в `/installation` только для чтения;
- `backup-config` с настройками и доступами к внешнему S3 — только для чтения;
- отдельные каталоги состояния и временных архивов — для записи;
- Docker socket для остановки и запуска остальных сервисов своей установки.

Доступ к Docker socket даёт контроллеру полномочия управления Docker на хосте.
Само приложение Альберта этот доступ не получает. Контроллер проверяет реальные
пути данных работающих контейнеров и использует имя собственного Compose project,
поэтому иной путь внутри контейнера и `docker compose -p ...` поддерживаются.
Логи `backup` используют независимый Docker logging driver `local` и доступны,
даже когда основной log-gateway остановлен.

1. **На машине восстановления** создай приватный ключ. Подставь полный адрес
   опубликованного образа `backup`:

   ```sh
   mkdir -p /safe/albert-keys
   docker run --rm \
     --mount type=bind,src=/safe/albert-keys,dst=/keys \
     <образ-backup> keygen --identity /keys/albert-backup.agekey
   ```

   Команда выводит только публичный recipient `age1…`.
   Приватный файл сохрани отдельно от сервера и бакета: он нужен для восстановления,
   а для создания копий достаточно публичного ключа.

2. В каталоге установки создай `backup-config`. Сохрани в нём образцы из того же
   коммита: `deploy/backup.example.json` как `config.json`,
   `deploy/backup-s3.example.json` как `s3.json`. Например, из checkout:

   ```sh
   sudo install -d -m 0700 backup-config
   sudo install -m 0600 deploy/backup.example.json backup-config/config.json
   sudo install -m 0600 deploy/backup-s3.example.json backup-config/s3.json
   ```

   В `config.json` заполни внешний S3 и публичный `age_recipient`, выбери время,
   IANA часовой пояс и `keep_days` (1–3660). Для штатного контейнера оставь
   `root: /installation`, `work_dir: /var/lib/openalbert-backup` и
   `credentials_file: /etc/openalbert-backup/s3.json`. Реальный путь установки
   на хосте контроллер определяет из своего монтирования. В checkout укажи
   `compose_file: deploy/compose.yaml` (или `deploy/compose.local.yaml`);
   для установки без исходников оставь `compose.yaml`.

   Endpoint задаётся как `host[:port]` без схемы, TLS — через `s3_secure`.
   В `s3.json` заполни `access_key`, `secret_key` и при необходимости `session_token`.
   Эти файлы не попадают в Git, публичное состояние и контекст модели.

3. Запусти контроллер вместе с остальными сервисами:

   ```sh
   docker compose --profile backup pull
   docker compose --profile backup up -d
   docker compose logs --tail=30 backup
   ```

   Можно добавить `backup` в `COMPOSE_PROFILES` в `.env`, сохранив остальные профили,
   например `COMPOSE_PROFILES=local-stt,backup`. Тогда профиль не нужно передавать
   флагом. В checkout добавляй `--project-directory . -f deploy/compose.yaml`
   (или `deploy/compose.local.yaml`) во все команды Compose; резервирование
   требует доступных registry digests образов сохраняемых сервисов.

Каталог `container_data/backup-work` должен вмещать полный зашифрованный архив.
Утилита проверяет запас места до остановки сервисов. Расписание работает внутри
контейнера: после перезапуска выполняется одна пропущенная попытка, если сохранённый
срок уже наступил. При первой установке без прошлого состояния контроллер ждёт
ближайшего запланированного времени. Монитор проверяет состояние каждые пять минут.

Ручной запуск и просмотр доступных копий:

```sh
docker compose exec backup albert-backup request
docker compose exec backup albert-backup list
docker compose logs --tail=50 backup
```

Команда `request` ставит ручную попытку в очередь основного процесса контроллера;
результат виден в его журнале и состоянии Альберта. Одновременные ручной
и автоматический запуски исключены блокировкой.
После изменения расписания, числа дней или других настроек перезапусти только
контроллер: `docker compose restart backup`. Для отключения —
`docker compose stop backup`; если профиль прописан в `.env`, убери его оттуда.
Если раньше были включены хостовые systemd-таймеры, отключи оба таймера, чтобы
расписанием управлял один контейнер.

### Осведомлённость Альберта

Оба Compose подключают `container_data/backup-state` в `/data/backup-state`
**только для чтения**. Каталог создаётся при запуске; секретов в нём нет.
`BACKUP_STATE_DIR` задаёт путь вне Compose, пустое значение отключает интеграцию.
Приложение не получает Docker socket, доступы к backup-бакету или приватный ключ.

Перед каждым новым вызовом модели, включая продолжение задачи после перезапуска,
приложение добавляет в контекст владельца свежий служебный блок: расписание,
следующий запуск, этап, время обновления, последнюю проверенную копию и известные
даты. В группах и чужих личных чатах этих данных нет. `backup_status` читает тот же
локальный снимок по запросу; это не live-запрос к S3 и не команда запуска бэкапа.

События начала, завершения, ошибки и отсутствия свежей копии запускают отдельный
Temporal Workflow в личном разговоре владельца, даже без входящего сообщения
и при `INITIATIVE_INTERVAL=0`. Событие начала позволяет предупредить о паузе;
готовность LLM и доставка предупреждения не задерживают бэкап сверх `notice_seconds`.
Во время остановки события остаются на диске и обрабатываются после запуска.
Идентификаторы и checkpoints предотвращают повторную постановку; Telegram offset
не меняется. Если владелец ещё не начал личный разговор, события ожидают его появления.

Штатный успех не требует уведомления. Ошибки и отсутствие свежей копии — повод
сообщить владельцу. При ошибке самой LLM приложение ставит краткое служебное
предупреждение в обычную очередь доставки. Старое начало не выдаётся за предстоящую
паузу; события старше 48 часов не вызывают запоздалые уведомления. Spool хранит до 90 дней событий.
Heartbeat обновляется каждые 15 секунд. Этап без heartbeat более пяти минут,
расписание, просроченное более двух часов, и недоступный файл дают `unknown`.
Монитор сообщает также об отсутствии успешной копии более 26 часов.

### Восстановление выбранной копии

На машине восстановления нужны Docker, конфигурация доступа к backup-бакету
и приватный ключ. Восстановление можно выполнить отдельным запуском образа `backup`.
Docker socket этому запуску не нужен. Подставь абсолютные пути на этой машине
и полный адрес опубликованного образа вместо `<образ-backup>`:

```sh
sudo mkdir -p /opt/recovery
docker run --rm \
  --mount type=bind,src=/safe/backup-config,dst=/etc/openalbert-backup,readonly \
  <образ-backup> list
docker run --rm \
  --mount type=bind,src=/safe/backup-config,dst=/etc/openalbert-backup,readonly \
  --mount type=bind,src=/safe/albert-backup.agekey,dst=/run/recovery.agekey,readonly \
  --mount type=bind,src=/opt/recovery,dst=/restore \
  <образ-backup> restore --id <идентификатор-из-list> \
  --identity /run/recovery.agekey --destination /restore/openalbert
```

На хосте данные появятся в `/opt/recovery/openalbert`. Этот каталог **не должен
существовать** до восстановления. Команда проверяет SHA-256, размер зашифрованных
байтов и целостность расшифрованного потока, сохраняет владельцев и права.
Выход из каталога и символические ссылки запрещены. При ошибке неполный каталог
удаляется. Сервисы автоматически не запускаются. Если в манифесте `compose_file` указан путь
в `deploy/`, используй его вместо `compose.yaml` в командах ниже и добавь
`--project-directory .`. Для локального Compose запускай с `--no-build`: исходники
приложений не входят в архив, используются сохранённые digest образов.

`compose.backup-images.json` фиксирует digest образов из манифеста. Проверь `.env`,
`backup-manifest.json`, совместимость архитектуры и доступ к registry. Останови
прежнюю установку с тем же Telegram-токеном. Перед первым запуском убери `backup`
из `COMPOSE_PROFILES` в восстановленном `.env`, сохранив остальные профили,
либо заранее создай `backup-config`. Затем:

```sh
cd /opt/recovery/openalbert
docker compose -f compose.yaml -f compose.backup-images.json config -q
docker compose -f compose.yaml -f compose.backup-images.json pull
docker compose -f compose.yaml -f compose.backup-images.json up -d
docker compose -f compose.yaml -f compose.backup-images.json ps
```

После переноса заново создай `backup-config` и включи профиль `backup`,
если нужно возобновить расписание. Путь `root` внутри контроллера остаётся
`/installation` независимо от каталога на хосте. Старые status/events из архива
не восстанавливаются. При ежедневном расписании можно потерять изменения с последней копии — штатно до суток; ошибки
увеличивают этот интервал. Восстановление Temporal не отменяет уже выполненные
внешние действия, включая сообщения с неопределённым исходом доставки.

Периодически проверяй восстановление в изолированной установке с отключёнными
реальными Telegram/LLM API. Проверки реализации:

```sh
task test:go
task test:backup
```

Smoke запускает настоящий образ `backup`, проверяет, что контроллер не
останавливается при резервировании, использует реальные PostgreSQL и два MinIO,
восстанавливает три базы, память и вложение, проверяет ротацию и повреждение объекта. Процессы приложения и Temporal
в этом storage-тесте заменены ожидающими контейнерами; модельные события проверяются
отдельно Temporal test harness. Docker-тест не читает рабочий `.env`.

### Ручная холодная копия

Для небольшой установки подходит холодная копия всего каталога: остановка
сервисов сохраняет PostgreSQL, Temporal и S3 в согласованном состоянии. Архив
содержит `.env` с ключами; храни его вне публичного репозитория и сервера приложения.
На Linux из каталога установки:

Если контроллер `backup` включён, сначала останови его: `docker compose stop backup`.
Это позволяет закончить аварийный запуск сервисов перед их общей остановкой.

```sh
docker compose stop
sudo tar --numeric-owner -czf "../openalbert-backup-$(date +%Y%m%d-%H%M%S).tar.gz" .env compose.yaml container_data
docker compose up -d
```

Перед восстановлением останови прежнюю установку. Распакуй архив в пустой каталог
на Linux, сохраняя владельцев файлов, затем запусти ту же версию образов:

```sh
sudo tar --numeric-owner -xzf /path/to/openalbert-backup.tar.gz
docker compose config -q
docker compose pull
docker compose up -d
docker compose ps
```

Закрепляй SHA-тег перед созданием копии: `master` может указывать на более новые
образы. Периодическое создание копий, их хранение вне сервера и проверку
восстановления нужно настроить для конкретной установки.

## Проверки и диагностика

```sh
task --list
task check
task test
task images
task verify
task reports
```

Каждый прогон сохраняет отдельный каталог `reports/local/<run-id>/` с
`summary.md`, `result.json`, логами этапов, HTML/JUnit-отчётами Playwright и
диагностикой VM. Подробнее — [локальные проверки](local-checks.md).

Для сквозного теста уже собранных образов можно вызвать `python3 tools/smoke/release-smoke.py`
с `--image компонент=тег` для каждого из пяти компонентов (без STT).
Проверка использует отдельный Compose project, временные данные и случайные
локальные порты; реальные ключи и `.env` проекта не читает. Веса STT не скачиваются.

Официальные справочники: [Docker Bake](https://docs.docker.com/build/bake/),
[сборки нескольких архитектур](https://docs.docker.com/build/building/multi-platform/),
[inline configs Compose](https://docs.docker.com/reference/compose-file/configs/).
