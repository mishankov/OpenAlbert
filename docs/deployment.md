# Готовые образы и публикация

[К содержанию](README.md)

Есть три способа запуска OpenAlbert:

- `deploy/compose.local.yaml` — локальная разработка: собирает четыре собственных образа из исходников.
- `deploy/compose.yaml` — установка готовых образов: не содержит `build` и не требует checkout.
- Автономный статический Go-бинарник `./openalbert` (`CGO_ENABLED=0`) без Docker — подробности в [руководстве разработки](development.md#работа-с-go-локально-и-запуск-голого-бинарника).

В checkout запускай Compose из корня репозитория с `--project-directory .`:
`docker compose --project-directory . -f deploy/compose.local.yaml up -d --build` для разработки
или `docker compose --project-directory . -f deploy/compose.yaml up -d` для готовых образов.
Так `.env`, контекст сборки и каталоги данных (`./data`, `./stt-models`, `./backup-state`,
`./backup-work`, `./backup-config`, `./computer/client`) остаются в корне репозитория.

Оба варианта Compose используют одинаковые сервисы, настройки, каталоги данных и локальный порт `8080`.
Их соответствие проверяет `python3 tools/checks/check-compose.py`. Не запускай оба варианта
одновременно с одним Telegram-токеном или общим каталогом `./data`.

## Какие образы собираем

Релизный каталог состоит ровно из **четырёх образов** без сторонних серверов БД, очередей,
объектного хранилища или логов:

- **`openalbert`** — статический Go-бинарник (`CGO_ENABLED=0`) со встроенной pure-Go SQLite
  (`DATA_DIR/openalbert.db`, режим WAL), локальным хранилищем артефактов (`DATA_DIR/artifacts`),
  встроенным оркестратором, журналом `openalbert_logs`, инспектором и Chromium из Alpine.
- **`stt`** — NeMo-Speech.cpp, Go-адаптер, FFmpeg и bootstrap (профиль `local-stt`). Веса
  скачиваются при запуске и хранятся в `./stt-models`; в образ не включаются.
- **`tts`** — HTTP-сервис синтеза речи Piper и FFmpeg Ogg/Opus с зафиксированной русской моделью
  (профиль `local-tts`).
- **`backup`** — минимальный Alpine-образ с Go-утилитой `albert-backup` (`CGO_ENABLED=0`)
  для онлайн-резервирования SQLite (`VACUUM INTO`) и данных во внешний S3 без Docker socket
  (профиль `backup`).

При пустом `COMPOSE_PROFILES` запускается единственный контейнер `openalbert`.

## Локальная сборка и публикация

Все проверки и сборки выполняются локально через Task и Docker Buildx Bake.
Полный каталог команд, установка инструментов и отчёты описаны в
[локальных проверках](local-checks.md).

```sh
task verify
```

Команда проверяет форматирование, Go analysis, Compose, Go race-тесты со встроенной SQLite
и настоящими Chromium/FFmpeg, онлайн-бэкап/восстановление, документацию и браузерные
сценарии. Затем собирает четыре образа для архитектуры Docker engine, запускает smoke
каждого образа и чистое развёртывание с перезапуском. Telegram/LLM заменены синтетическими API,
рабочий `.env` не читается, веса STT не скачиваются. Отдельный `task test:computer` проверяет
SSH-адаптер и независимость пользовательского компьютера; его одноразовый образ не публикуется.

Публикация запускается отдельно, из чистого checkout ветки `master`:

```sh
docker login ghcr.io
OPENALBERT_IMAGE_PREFIX=ghcr.io/mishankov/openalbert task publish
```

`task publish` сам повторяет все проверки и собирает/проверяет **обе** архитектуры
`linux/amd64` и `linux/arm64`, включая чистое развёртывание каждой.
На Apple Silicon AMD64 использует эмуляцию и может собираться значительно дольше.
Образы загружаются только после успешной проверки всех этапов. Авторизация — локальный
Docker credential store; namespace задаётся явно через `OPENALBERT_IMAGE_PREFIX`.

Каждый компонент получает теги `sha-<полный SHA>-amd64` и `sha-<полный SHA>-arm64`,
после чего создаются общие манифесты `sha-<полный SHA>` и `master`:

```text
ghcr.io/<owner>/<repository>/openalbert:sha-<полный SHA>
ghcr.io/<owner>/<repository>/stt:sha-<полный SHA>
ghcr.io/<owner>/<repository>/tts:sha-<полный SHA>
ghcr.io/<owner>/<repository>/backup:sha-<полный SHA>
```

Для воспроизводимой установки выбирай SHA-тег от полностью успешного локального
прогона. Публикация нескольких пакетов не атомарна: при ошибке повтори `task publish`
из того же коммита и дождись общего успеха. На сервер ничего автоматически не развёртывается.
Проверь видимость каждого GHCR package: для анонимного pull пакет должен быть public;
для закрытых пакетов на сервере нужен `docker login ghcr.io` с правом чтения.

## Установка без исходников

Нужны Docker Engine, Docker Compose **2.24.0 или новее**, Linux AMD64 или ARM64,
свободный локальный порт `8080` и постоянный диск. Указанная версия Compose поддерживает
необязательный `models.env` и `depends_on.required: false`. Для Raspberry Pi выбирай
64-битную ОС и SSD для данных; скорость локального STT/TTS и параллельных браузеров
на Pi следует замерить под свою нагрузку.

Скачай `deploy/compose.yaml` из выбранного коммита как `compose.yaml`
в каталог установки и положи рядом `.env.release.example` из корня репозитория и
`deploy/models.example.toml` как `models.example.toml`. Дальнейшие команды этого раздела
выполняются в каталоге установки без исходников:

```sh
cp .env.release.example .env
cp models.example.toml models.toml
mkdir -p data/knowledge data/chatgpt backup-state
sudo chown -R 10001:10001 data
sudo chmod 700 data/chatgpt
```

В `.env` укажи `OPENALBERT_IMAGE_PREFIX=ghcr.io/<owner>/<repository>` в нижнем регистре
и `OPENALBERT_IMAGE_TAG=sha-<полный SHA коммита>` либо `master`. Заполни Telegram token,
разрешённые ID и ключ модели. В `models.toml` задай фактический model ID, endpoint,
возможности и лимиты; [маршруты ролей](model-routing.md) выбираются только в этом файле.
Compose подключает его только для чтения; отсутствующий файл запрещает запуск.
Дополнительные ключи профилей помести в `models.env` рядом с `.env` (`chmod 600 models.env`);
файл необязателен и включается в зашифрованный backup. Пустые обязательные значения
Compose отвергает до создания контейнеров.

```sh
docker compose config -q
docker compose pull
docker compose up -d
docker compose ps
```

Примеры настроек включают локальный STT через `COMPOSE_PROFILES=local-stt`.
Первый запуск скачивает около 742 МБ весов в `./stt-models` и прогревает модель. Бот может
запуститься раньше готовности STT; перед голосовыми сообщениями дождись `healthy`.
Для **минимального режима одного контейнера** (без локального STT) задай `COMPOSE_PROFILES=`
и `STT_BASE_URL=`. Для внешнего STT оставь `COMPOSE_PROFILES=` и укажи его `STT_BASE_URL`,
модель и ключ. При изменении уже работающей установки останови локальный STT командой
`docker compose --profile local-stt stop stt`, затем выполни `docker compose up -d`.
Одна смена URL не отключает профиль; `--remove-orphans` не останавливает сервисы
из отключённых профилей.

Данные Альберта сохраняются в едином каталоге `./data`: SQLite-база `openalbert.db`,
локальные артефакты `artifacts/`, Markdown-память и `SOUL.md` в `knowledge/`, токены
плана ChatGPT в `chatgpt/`. Веса STT хранятся отдельно в `./stt-models`. Компьютер
пользователь создаёт и обслуживает отдельно; по умолчанию SSH-инструменты выключены.
Основной Compose не содержит `computer` или `computer-init`, а релизы не собирают и
не публикуют их образ. Подключение и перенос — в [руководстве компьютера](computer.md).

Порт `8080` опубликован только на `127.0.0.1`; удалённый доступ к инспектору можно
организовать SSH-туннелем. Telegram использует исходящий polling, проброс входящего
порта для бота не нужен.

Например, `ssh -N -L 8080:127.0.0.1:8080 user@server` открывает инспектор на
`http://localhost:8080/inspect/`. Если используешь другой локальный порт, задай
соответствующий `INSPECTOR_PUBLIC_URL`, чтобы ссылки бота вели на доступный адрес.

Для прямого доступа из доверенной LAN замени публикацию порта сервиса `openalbert`
на `"192.168.1.31:8080:8080"`, указав LAN-адрес своего сервера, и пересоздай
приложение: `docker compose up -d --no-deps --force-recreate openalbert`.
`INSPECTOR_PUBLIC_URL=http://192.168.1.31:8080/inspect/` задаёт только адрес ссылок.
Проверок Host/Origin и авторизации в инспекторе нет; доступ регулируется публикацией
порта в Compose. Подробности — [инспектор](inspector.md).

## Обновление установки

Если используешь прежний встроенный `computer`, сначала выполни
[перенос с сохранением системного диска](computer.md#перенос-прежнего-встроенного-компьютера).
Отдельный компьютер при дальнейших обновлениях не затрагивается.

Сделай резервную копию данных, возьми актуальный `compose.yaml` и пример настроек
из нужного коммита, задай общий SHA-тег и выполни:

```sh
docker compose pull
docker compose up -d
```

Не выполняй параллельно `up` из локального Compose. Возврат к старым образам
возможен только с учётом совместимости схемы SQLite; для обратного несовместимого
изменения нужна соответствующая резервная копия.

## Резервная копия и восстановление

### Автоматические копии в S3

`albert-backup` работает **в отдельном контейнере `backup`** с корневой ФС только для чтения
(`read_only: true`), **без Docker socket** и **без остановки OpenAlbert**. В контейнере
находятся статическая Go-утилита, расписание и монитор; на хосте достаточно Docker Compose.
Для этой схемы нужен отдельный внешний S3-совместимый бакет.

Контроллер снимает согласованный **онлайн-снимок SQLite** через `VACUUM INTO` прямо
во время работы приложения (режим WAL обеспечивает чтение без блокировки диалогов и
нулевой простой сервиса). В зашифрованный архив входят:

- согласованный снимок SQLite `data/openalbert.db` (полученный через `VACUUM INTO`);
- локальные артефакты `data/artifacts/`;
- `data/knowledge/`: память, `SOUL.md`, `USER.md`, `GROUP.md`, профили участников и skills;
- `.env`, выбранный Compose-файл (`compose.yaml`), `models.toml`, необязательный `models.env` с дополнительными ключами и манифест резервной копии.

Токены ChatGPT (`data/chatgpt/`), скачиваемые веса STT (`./stt-models`), временные архивы
(`./backup-work`), состояние бэкапов (`./backup-state`) и каталог настроек `./backup-config`
не архивируются. Внешний компьютер, его системный диск и ключи вне установки также не входят
в копию; см. [резервирование компьютера](computer.md#резервирование-и-проверки).
Символические ссылки и выход за пределы каталога установки отклоняются.

Архив сжимается и сразу шифруется [age](https://age-encryption.org/) публичным
X25519-ключом; открытый архив на диске не создаётся. Приложение продолжает отвечать
пользователям и выполнять задачи на протяжении всего резервирования.

После загрузки утилита полностью читает зашифрованный объект из S3 и сравнивает
размер и SHA-256. Только затем создаётся `complete.json`, и копия считается успешной.
Проверка передачи байтов не заменяет проверку восстановления.

`keep_days` — число **разных дат с успешными копиями** в настроенном часовом поясе.
При 14 сохраняются все копии за последние 14 успешных дат; несколько ручных запусков
за день не вытесняют предыдущие даты. Пропущенные дни и ошибки не учитываются.
Ротация выполняется только после новой проверенной копии.
Оставшиеся после обрыва загрузки объекты без `complete.json` старше 48 часов
удаляются после успешного запуска; незавершённые multipart очищает правило бакета.

Используй отдельный prefix для каждой установки и непубличный внешний бакет
с изначально выключенным versioning. Включённое или suspended versioning
отклоняется, иначе удаление оставляло бы оплачиваемые версии. Аккаунту нужны права
проверки бакета и versioning, перечисления, чтения, записи, удаления объектов
и отмены multipart-загрузок в выделенной области. Не назначай этому prefix
возрастную Lifecycle-ротацию завершённых копий: она удаляла бы их независимо от
числа успешных дней. Отдельное правило удаления незавершённых multipart допустимо.

### Настройка контейнера резервирования

`backup` включается отдельным профилем Compose. Ему передаются только необходимые
файловые монтирования (Docker socket не монтируется):

- каталог установки (`.`) в `/installation` только для чтения;
- `./data` в `/installation/data` (для онлайн-снимка SQLite WAL и чтения артефактов/знаний);
- `./backup-config` в `/etc/openalbert-backup` только для чтения;
- `./backup-state` в `/installation/backup-state` для записи состояния и событий;
- `./backup-work` в `/var/lib/openalbert-backup` для временной сборки зашифрованного архива.

Само приложение Альберта получает только `./backup-state` в `/data/backup-state`
в режиме только для чтения; доступов к внешнему S3 и ключа шифрования у него нет.
Логи `backup` используют встроенный Docker logging driver `local` и доступны через
`docker compose logs backup`.

1. **На машине восстановления** создай приватный ключ. Подставь полный адрес
   опубликованного образа `backup`:

   ```sh
   mkdir -p /safe/albert-keys
   docker run --rm \
     --mount type=bind,src=/safe/albert-keys,dst=/keys \
     <образ-backup> keygen --identity /keys/albert-backup.agekey
   ```

   Команда выводит только публичный recipient `age1…`.
   Приватный файл сохрани отдельно от сервера и бакета: он нужен для восстановления,
   а для создания копий достаточно публичного ключа.

2. В каталоге установки создай `backup-config`. Сохрани в нём образцы из того же
   коммита: `deploy/backup.example.json` как `config.json`,
   `deploy/backup-s3.example.json` как `s3.json`. Например, из checkout:

   ```sh
   sudo install -d -m 0700 backup-config
   sudo install -m 0600 deploy/backup.example.json backup-config/config.json
   sudo install -m 0600 deploy/backup-s3.example.json backup-config/s3.json
   ```

   В `config.json` заполни внешний S3 и публичный `age_recipient`, выбери время,
   IANA часовой пояс и `keep_days` (1–3660). Для штатного контейнера оставь
   `root: /installation`, `work_dir: /var/lib/openalbert-backup`, `notice_seconds: 0`
   (простоя нет) и `credentials_file: /etc/openalbert-backup/s3.json`. В checkout укажи
   `compose_file: deploy/compose.yaml` (или `deploy/compose.local.yaml`);
   для установки без исходников оставь `compose.yaml`.

   Endpoint задаётся как `host[:port]` без схемы, TLS — через `s3_secure`.
   В `s3.json` заполни `access_key`, `secret_key` и при необходимости `session_token`.
   Эти файлы не попадают в Git, публичное состояние и контекст модели.

3. Запусти контроллер вместе с остальными сервисами:

   ```sh
   docker compose --profile backup pull
   docker compose --profile backup up -d
   docker compose logs --tail=30 backup
   ```

   Можно добавить `backup` в `COMPOSE_PROFILES` в `.env`, сохранив остальные профили,
   например `COMPOSE_PROFILES=local-stt,backup`. Тогда профиль не нужно передавать
   флагом. В checkout добавляй `--project-directory . -f deploy/compose.yaml`
   (или `deploy/compose.local.yaml`) во все команды Compose.

Каталог `./backup-work` должен вмещать временный снимок и зашифрованный архив.
Утилита проверяет запас места перед началом копирования. Расписание работает внутри
контейнера: после перезапуска выполняется одна пропущенная попытка, если сохранённый
срок уже наступил. При первой установке без прошлого состояния контроллер ждёт
ближайшего запланированного времени. Монитор проверяет состояние каждые пять минут.

Ручной запуск и просмотр доступных копий:

```sh
docker compose exec backup albert-backup request
docker compose exec backup albert-backup list
docker compose logs --tail=50 backup
```

Команда `request` ставит ручную попытку в очередь основного процесса контроллера;
результат виден в его журнале и состоянии Альберта. Одновременные ручной
и автоматический запуски исключены блокировкой.
После изменения расписания, числа дней или других настроек перезапусти только
контроллер: `docker compose restart backup`. Для отключения —
`docker compose stop backup`; если профиль прописан в `.env`, убери его оттуда.

### Осведомлённость Альберта

Оба Compose подключают `./backup-state` в `/data/backup-state` **только для чтения**.
Каталог создаётся при запуске; секретов в нём нет. `BACKUP_STATE_DIR` задаёт путь вне
Compose, пустое значение отключает интеграцию. Приложение не получает доступы к
backup-бакету или приватный ключ.

Перед каждым новым вызовом модели, включая продолжение задачи после перезапуска,
приложение добавляет в контекст владельца свежий служебный блок: расписание,
следующий запуск, этап, время обновления, последнюю проверенную копию и известные
даты. В группах и чужих личных чатах этих данных нет. `backup_status` читает тот же
локальный снимок по запросу; это не live-запрос к S3 и не команда запуска бэкапа.

События начала, завершения, ошибки и отсутствия свежей копии обрабатываются
встроенным оркестратором в личном разговоре владельца, даже без входящего сообщения
и при `INITIATIVE_INTERVAL=0`. Идентификаторы событий и checkpoints предотвращают
повторную постановку; Telegram offset не меняется. Если владелец ещё не начал личный
разговор, события ожидают его появления.

Штатный успех не требует уведомления. Ошибки и отсутствие свежей копии — повод
сообщить владельцу. При ошибке самой LLM приложение ставит краткое служебное
предупреждение в обычную очередь доставки. События старше 48 часов не вызывают
запоздалые уведомления. Spool хранит до 90 дней событий.
Heartbeat обновляется каждые 15 секунд. Этап без heartbeat более пяти минут,
расписание, просроченное более двух часов, и недоступный файл дают `unknown`.
Монитор сообщает также об отсутствии успешной копии более 26 часов.

### Восстановление выбранной копии

На машине восстановления нужны Docker, конфигурация доступа к backup-бакету
и приватный ключ. Восстановление выполняется отдельным запуском образа `backup`.
Подставь абсолютные пути на этой машине и полный адрес опубликованного образа вместо `<образ-backup>`:

```sh
sudo mkdir -p /opt/recovery
docker run --rm \
  --mount type=bind,src=/safe/backup-config,dst=/etc/openalbert-backup,readonly \
  <образ-backup> list
docker run --rm \
  --mount type=bind,src=/safe/backup-config,dst=/etc/openalbert-backup,readonly \
  --mount type=bind,src=/safe/albert-backup.agekey,dst=/run/recovery.agekey,readonly \
  --mount type=bind,src=/opt/recovery,dst=/restore \
  <образ-backup> restore --id <идентификатор-из-list> \
  --identity /run/recovery.agekey --destination /restore/openalbert
```

На хосте данные появятся в `/opt/recovery/openalbert` (включая `data/openalbert.db`,
`data/artifacts/`, `data/knowledge/`, `.env`, `models.toml` и `compose.yaml`). Этот
каталог **не должен существовать** до восстановления. Команда проверяет SHA-256, размер
зашифрованных байтов и целостность расшифрованного потока, сохраняет владельцев и права.
Выход из каталога и символические ссылки запрещены. При ошибке неполный каталог удаляется.
Сервисы автоматически не запускаются.

Проверь `.env` и `backup-manifest.json`. Останови прежнюю установку с тем же Telegram-токеном.
Перед первым запуском убери `backup` из `COMPOSE_PROFILES` в восстановленном `.env`,
сохранив остальные профили, либо заранее создай `backup-config`. Затем запусти установку:

```sh
cd /opt/recovery/openalbert
docker compose config -q
docker compose pull
docker compose up -d
docker compose ps
```

После переноса при необходимости заново войди в план ChatGPT (`/chatgpt login`), создай
`backup-config` и включи профиль `backup`. Старые status/events из архива не
восстанавливаются. При ежедневном расписании можно потерять изменения с последней копии —
штатно до суток; ошибки увеличивают этот интервал. Восстановление базы не отменяет уже
выполненные внешние действия, включая сообщения с неопределённым исходом доставки.

Периодически проверяй восстановление в изолированной установке с отключёнными
реальными Telegram/LLM API. Проверки реализации:

```sh
task test:go
task test:backup
```

Smoke запускает настоящий образ `backup`, проверяет онлайн-снимок SQLite через
`VACUUM INTO` без остановки приложения, восстановление базы, памяти и артефактов,
ротацию и обнаружение повреждения объекта. Docker-тест не читает рабочий `.env`.

### Ручная копия

Для небольшой установки можно скопировать каталог данных вручную. Для согласованной
копии либо останови `openalbert`, либо сними онлайн-снимок SQLite через `VACUUM INTO`.
Архив содержит `.env` с ключами; храни его вне публичного репозитория и сервера приложения.
На Linux из каталога установки:

```sh
docker compose stop openalbert
sudo tar --numeric-owner -czf "../openalbert-backup-$(date +%Y%m%d-%H%M%S).tar.gz" .env models.toml compose.yaml data
docker compose up -d openalbert
```

Если используется `models.env`, добавь его в список файлов команды `tar` выше; при другом
пути TOML укажи фактический файл вместо `models.toml`.

Перед восстановлением останови прежнюю установку. Распакуй архив в пустой каталог
на Linux, сохраняя владельцев файлов, затем запусти ту же версию образов:

```sh
sudo tar --numeric-owner -xzf /path/to/openalbert-backup.tar.gz
docker compose config -q
docker compose pull
docker compose up -d
docker compose ps
```

Закрепляй SHA-тег перед созданием копии: `master` может указывать на более новые
образы. Периодическое создание копий, их хранение вне сервера и проверку
восстановления нужно настроить для конкретной установки.

## Проверки и диагностика

```sh
task --list
task check
task test
task images
task verify
task reports
```

Каждый прогон сохраняет отдельный каталог `reports/local/<run-id>/` с
`summary.md`, `result.json`, логами этапов, HTML/JUnit-отчётами Playwright и
диагностикой проверок. Подробнее — [локальные проверки](local-checks.md).

Для сквозного теста уже собранных образов можно вызвать `python3 tools/smoke/release-smoke.py`.
Проверка использует отдельный Compose project, временные данные и случайные
локальные порты; реальные ключи и `.env` проекта не читает. Веса STT не скачиваются.

Официальные справочники: [Docker Bake](https://docs.docker.com/build/bake/),
[сборки нескольких архитектур](https://docs.docker.com/build/building/multi-platform/).
