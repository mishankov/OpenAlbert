# Обновления приложения macOS

Используется тот же механизм, что в polka: Sparkle 2, HTTPS appcast в GitHub
Releases, ZIP с Ed25519-подписью и отдельное подтверждение установки. Ключи polka
не используются. API Альберта и его Bearer-токен не участвуют в обновлении клиента.

Приложение проверяет релизы в фоне и загружает найденное обновление. Установка
возможна только по команде пользователя после сохранения черновика и кеша на
диск. Во время отправки, загрузки/сохранения файла, подключения или IME composition
установка недоступна. Обычный выход отменяет подготовленную установку. Без
`SUFeedURL` и `SUPublicEDKey` сборка работает как локальная, без сетевых проверок.

«Альберт → Обновления…» (⌘⇧U) открывает небольшое окно со статусом, версией и
кнопкой проверки (⌘R) или установки и перезапуска (⌘Return). Escape закрывает
окно, сохраняя загруженное обновление. Автоматическая установка при выходе
отключена; перезапуск требует явной команды.

## Контракт release-сборки

Сборка: `apps/macos/build-app.sh [debug|release]`. Версия берётся из
`apps/macos/version.json` (`version`: semver, `build`: положительное целое).
Повторное использование build для другого архива запрещено процессом релиза.

Релизные параметры: `ALBERT_UPDATE_FEED_URL` (HTTPS), `SPARKLE_PUBLIC_KEY`
(base64 Ed25519, 32 байта). Они задаются вместе и попадают в Info.plist как
`SUFeedURL` и `SUPublicEDKey`. Без них обновления отключены. Публичная лента:
`https://github.com/mishankov/OpenAlbert/releases/latest/download/appcast.xml`.

Скрипт упаковки `apps/macos/release.py` создаёт ZIP, appcast.xml и checksums.txt
в `apps/macos/build/release`. Он требует `SPARKLE_PRIVATE_KEY` для подписи,
проверяет подпись опубликованных байт против встроенного публичного ключа,
версию и размер архива. При ошибке релиз не создаётся. Закрытый ключ передаётся
Sparkle через stdin, не сохраняется в исходниках и не печатается в логах.

Публикация отделена от сборки: workflow готовит GitHub draft release с артефактами.
Публикация draft делает appcast доступным установленным клиентам. ZIP-архивы
версий неизменяемы. Для релиза нужна стабильная подпись приложения одним
сертификатом, чтобы обновления сохраняли идентичность приложения и доступ к
Keychain; ad-hoc сборка предназначена только для разработки.

## Однократная настройка

В GitHub Environment `macos-release` задай следующие параметры:

| Тип | Имя | Значение |
| --- | --- | --- |
| Variable | `SPARKLE_PUBLIC_KEY` | Публичный Ed25519-ключ Альберта в base64 |
| Secret | `SPARKLE_PRIVATE_KEY` | Экспорт закрытого ключа Sparkle в base64 |
| Variable | `ALBERT_SIGNING_CERT_SHA1` | SHA-1 постоянного сертификата Code Signing, 40 hex-символов без двоеточий |
| Secret | `ALBERT_SIGNING_P12` | PKCS#12 с сертификатом и закрытым ключом, закодированный base64 без переводов строки |
| Secret | `ALBERT_SIGNING_PASSWORD` | Пароль этого PKCS#12 |

После `swift package --package-path apps/macos resolve` инструменты Sparkle
находятся в `apps/macos/.build/artifacts/sparkle/Sparkle/bin`. Для нового ключа
используй отдельный account `ru.mishankov.albert.desktop`:

```sh
apps/macos/.build/artifacts/sparkle/Sparkle/bin/generate_keys --account ru.mishankov.albert.desktop
```

Команда сохраняет новый ключ в Keychain и показывает публичный ключ. Экспорт
через `generate_keys --account ru.mishankov.albert.desktop -x /private/path/key.txt`
предназначен для переноса в GitHub Secret и резервную копию; путь должен быть
вне репозитория. Не запускай генератор с account по умолчанию: он может выбрать
ключ другого приложения.

Для подписи `.app` выдели отдельный постоянный сертификат Code Signing —
Developer ID либо self-signed, как в polka. Его можно создать через Certificate
Assistant в Keychain Access и экспортировать вместе с закрытым ключом в PKCS#12.
Self-signed релизы не нотариализованы Apple; первоначальное открытие может
потребовать разрешения macOS. Не меняй сертификат между обычными версиями.
CI импортирует его во временный Keychain, проверяет fingerprint и срок действия,
подписывает приложение и вложенные помощники, затем удаляет временный Keychain.

## Выпуск версии

1. Обнови `version` и увеличь `build` в `apps/macos/version.json`. Стабильная
   лента принимает версии вида `0.1.1`, без prerelease и build metadata.
2. Запусти workflow **macOS draft release** с тегом `macos-v0.1.1`. Сборка
   проверит тесты, подписи, идентичность приложения, переносимость bundle и
   предыдущие номера build, затем создаст draft release с ZIP/appcast/checksums.
3. Проверь draft и опубликуй его как последний стабильный GitHub Release.
   Существующий тег или релиз повторно не используется. Не заменяй ZIP после
   публикации; исправления выпускаются следующей версией/build.

Локальная подготовка с уже настроенными переменными выполняется через
`python3 apps/macos/release-signing.py`. Без ключей или при несовпадении
сертификата/подписи команда завершится ошибкой и не создаст релизные артефакты.
Она сама ничего не публикует.

## Проверки

`swift test --package-path apps/macos` проверяет отдельное подтверждение установки,
сохранение черновика и UUID, ошибки записи, занятые операции, IME и сочетания.
`python3 -m unittest discover -s apps/macos -p 'test_release.py' -v` использует
публичный тестовый ключ RFC8032: архив подписывается настоящим `sign_update`,
независимо проверяется CryptoKit и отклоняется после изменения байт, размера,
версии или ключа. Рабочие ключи для этих проверок не нужны.

Реальная установка опубликованного релиза требует настроенных ключей и двух
выпущенных версий. Тесты состояния и подписи не подменяют такую проверку.

Официальные справочники: [Sparkle](https://sparkle-project.org/documentation/)
и [программная интеграция](https://sparkle-project.org/documentation/programmatic-setup/).
