# Архитектура OpenAlbert

OpenAlbert — персональный AI-агент с собственной заданной пользователем личностью, долговременной памятью, несколькими каналами общения и возможностью выполнять работу на удалённых компьютерах. Он выполняет поручения в фоне и может самостоятельно заводить длительные задачи, опираясь на интересы пользователя.

Документы описывают архитектуру на уровне компонентов и процессов. В репозитории реализован MVP: Go-приложение, Temporal Workflows и Activities, PostgreSQL, Markdown-память, Telegram и внешние HTTP API. Практические команды и настройки находятся в [руководстве запуска](development.md). Схемы API и подробные поля контрактов остаются в коде.

## Границы MVP

- Первый интерфейс — Telegram. Desktop app и переход между личными каналами появятся позже; общая модель разговоров сохраняет такую возможность.
- Провайдер и модель LLM выбираются в настройках запуска OpenAlbert. Автоматический выбор модели для отдельных операций в MVP не предполагается.
- Среда запуска — Docker Compose.
- Computer box — отдельный Ubuntu-контейнер с SSH и `sudo` без пароля. Команды и обмен артефактами доступны личному чату владельца и его запланированным задачам.

## Согласованные принципы

1. Задача существует независимо от разговора, сессии и конкретного запуска агента. В новой сессии агент может найти её и получить актуальный статус через tools.
2. Личное общение продолжается между каналами, привязанными к одному пользователю. Telegram-группа представляет отдельный разговор.
3. Сессия выбирается по ключу разговора в хранилище. Семантический выбор сессии через LLM не требуется.
4. Агентский цикл оркестрируется Temporal. Вызовы LLM и инструментов выполняются как Activities.
5. Основной контейнер содержит Go-ядро и headless Chromium. Каждая интерактивная сессия и фоновый запуск получают независимый браузер. Рабочие программы запускаются в отдельном Ubuntu Computer box по SSH.
6. Always on включает фоновую работу и инициативу. OpenAlbert может самостоятельно создавать длительные задачи.
7. Характер задаёт пользователь. OpenAlbert самостоятельно его не меняет. Skills обсуждаются и формируются совместно; агент может предлагать изменения.
8. Память пополняется автоматически. После закрытия каждой сессии обязательно выполняется анализ пропущенных сведений и необходимых исправлений.
9. Все задачи и вся память постоянно в prompt не загружаются. Агент получает нужные сведения через инструменты.

## Технологические решения

- **Бэкенд — Go (Golang).** Для работы с Temporal используется Go SDK.
- **LLM — OpenAI-совместимые API.** Провайдер и модель выбираются в настройках запуска; ядро не привязывается к одной модели или одному провайдеру.
- **Развёртывание — Docker Compose.** Сервисы OpenAlbert и инфраструктура запускаются единым Compose-проектом.
- **Веб-поиск — необязательный Yandex Search API.** Без ключа и ID каталога OpenAlbert запускается без `web_search`; чтение публичных страниц через `web_read` остаётся доступным. Общий интерфейс поиска сохраняет возможность замены провайдера в дальнейшем.
- **Логирование — Wide Events.** Собственный код формирует широкие структурированные события по референсу Boris Tane [Logging Sucks](https://loggingsucks.com/).
- **Хранилище логов — VictoriaLogs.** Все контейнеры передают логи через Docker logging driver `splunk` в неблокирующем режиме.

## Хранение и исполнение MVP

В реализации приняты следующие решения:

- PostgreSQL хранит операционное состояние приложения отдельно от служебных данных Temporal.
- Текстовая память, профиль и skills доступны как Markdown; вложения и результаты работы хранятся в S3-совместимом хранилище.
- Надёжный приём сообщений и очередь исходящей доставки связывают каналы с исполнением.
- Состояние задач обновляется через единый механизм; каждый исполнитель сохраняет результат своего шага.
- Фоновая проверка интересов запускает ограниченную полезную работу и учитывает уже отправленные уведомления.

## Что ещё предстоит выбрать

- Точная организация памяти, правила отбора воспоминаний, забывания и разрешения противоречий.
- Постоянный том и резервирование Markdown-памяти, а также необходимость дополнительных поисковых индексов.
- Пределы допустимых самостоятельных действий. Возможность создать задачу сама по себе не выдаёт новые доступы.
- Настройка частоты фоновых запусков, бюджетов и инициативных уведомлений под реальное использование. Начальные пределы описаны в [руководстве запуска](development.md).

## Как читать схемы

В документах используются схемы компонентов и процессов, последовательности сообщений и диаграмма состояний. Они написаны на Mermaid; рядом с исходниками в [diagrams](diagrams) лежат SVG для обычных Markdown-просмотрщиков. Источником каждой иллюстрации является одноимённый файл `.mmd`.

Чтобы обновить SVG после изменения схемы, можно выполнить из папки `docs`:

```sh
npx --yes --package @mermaid-js/mermaid-cli@12.0.0 mmdc -i diagrams/components.mmd -o diagrams/components.svg -c diagrams/mermaid.config.json -b white --no-font-embed
```

Группы на схемах обозначают логические обязанности. Каждая группа не требует отдельного сервиса или контейнера.
