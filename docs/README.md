# Архитектура OpenAlbert

OpenAlbert — персональный AI-агент с собственной заданной пользователем личностью, долговременной памятью, несколькими каналами общения и возможностью выполнять работу на удалённых компьютерах. Он выполняет поручения в фоне и может самостоятельно заводить длительные задачи, опираясь на интересы пользователя.

Документы описывают архитектуру на уровне компонентов и процессов. В репозитории реализован MVP: единое Go-приложение со встроенным оркестратором, встроенной pure-Go SQLite (`DATA_DIR/openalbert.db`), локальным файловым хранилищем артефактов (`DATA_DIR/artifacts`), встроенным журналом `openalbert_logs`, Markdown-памятью, Telegram и внешними HTTP API. Практические команды и настройки находятся в [руководстве запуска](development.md). Схемы API и подробные поля контрактов остаются в коде.

## Границы MVP

- Telegram и клиентский HTTP API используют один личный разговор. API ограничен данными владельца.
- TOML связывает роли `chat`, `background` и `analysis` с именованными профилями LLM. Роль выбирает код приложения; каждая использует ровно одну модель без fallback.
- Среда запуска — Docker Compose (от минимального режима одного контейнера `openalbert` до набора с `stt`, `tts` и `backup`) либо автономный статический Go-бинарник `./openalbert` без внешних серверов БД, очередей или логов.
- Computer box — необязательная машина пользователя по SSH с независимым жизненным циклом. Команды и обмен артефактами доступны личному чату владельца и его запланированным задачам.

## Согласованные принципы

1. Задача существует независимо от разговора, сессии и конкретного запуска агента. В новой сессии агент может найти её и получить актуальный статус через tools.
2. Личное общение продолжается между каналами, привязанными к одному пользователю. Telegram-группа представляет отдельный разговор.
3. Сессия выбирается по ключу разговора в хранилище. Семантический выбор сессии через LLM не требуется.
4. Агентский цикл, таймеры, расписания и восстановление шагов оркестрируются встроенным Go-оркестратором поверх устойчивого состояния в SQLite.
5. Основной контейнер содержит Go-ядро и headless Chromium. Каждая интерактивная сессия и фоновый запуск получают независимый браузер. Рабочие программы запускаются в отдельном Ubuntu Computer box по SSH.
6. Always on включает фоновую работу и инициативу. OpenAlbert может самостоятельно создавать длительные задачи.
7. Характер задаёт пользователь. OpenAlbert самостоятельно его не меняет. Skills обсуждаются и формируются совместно; агент может предлагать изменения.
8. Память пополняется автоматически. После закрытия каждой сессии обязательно выполняется анализ пропущенных сведений и необходимых исправлений.
9. Все задачи и вся память постоянно в prompt не загружаются. Агент получает нужные сведения через инструменты.

## Технологические решения

- **Бэкенд — Go (Golang), `CGO_ENABLED=0`.** Единый процесс включает агентский цикл, встроенный оркестратор, планировщик задач, веб-инспектор и клиентский HTTP API.
- **Хранение состояния — встроенная pure-Go SQLite (`DATA_DIR/openalbert.db`, режим WAL).** Внешняя СУБД не требуется.
- **Артефакты — локальная файловая система (`DATA_DIR/artifacts`).** Вложения, скриншоты и результаты работы хранятся в каталоге данных без отдельного объектного сервера.
- **LLM — OpenAI-совместимые API и план ChatGPT.** Провайдер и модель выбираются в `models.toml`; ядро не привязывается к одной модели или одному провайдеру.
- **Развёртывание — Docker Compose (4 образа: `openalbert`, `stt`, `tts`, `backup`) или голый бинарник.** В минимальной конфигурации (`COMPOSE_PROFILES=""`) работает единственный контейнер `openalbert`.
- **Веб-поиск — необязательный Exa или Yandex Search API.** Подключается через `EXA_API_KEY` или `YANDEX_API_KEY` + `YANDEX_FOLDER_ID` (при наличии обоих выбор задаётся через `WEB_SEARCH_PROVIDER`). Без ключей OpenAlbert запускается без `web_search`; чтение публичных страниц через `web_read` и браузер остаются доступными. Настройка — в [руководстве запуска](development.md), подробности инструмента — в [начальных инструментах](tools.md).
- **Логирование — Wide Events + встроенная таблица SQLite `openalbert_logs`.** Собственный код формирует широкие структурированные события по референсу Boris Tane [Logging Sucks](https://loggingsucks.com/), пишет JSON в stdout/stderr и сохраняет события в `openalbert_logs` с хранением 30 дней; `logs_search` работает из коробки без внешнего хранилища логов.

## Хранение и исполнение MVP

В реализации приняты следующие решения:

- Встроенная SQLite (`DATA_DIR/openalbert.db`) хранит операционное состояние приложения, очереди, квитанции вызовов, расписания, трассы инспектора и операционный журнал `openalbert_logs`.
- Текстовая память, профиль и skills доступны как Markdown в `DATA_DIR/knowledge/`; вложения и результаты работы хранятся в `DATA_DIR/artifacts/`.
- Надёжный приём сообщений и очередь исходящей доставки связывают каналы с встроенным оркестратором.
- Состояние задач обновляется через единый механизм; каждый шаг сохраняет результат и контрольную точку для продолжения после перезапуска.
- Фоновая проверка интересов запускает ограниченную полезную работу и учитывает уже отправленные уведомления.

## Как читать схемы

В документах используются схемы компонентов и процессов, последовательности сообщений и диаграмма состояний. Они написаны на Mermaid; рядом с исходниками в [diagrams](diagrams) лежат SVG для обычных Markdown-просмотрщиков. Источником каждой иллюстрации является одноимённый файл `.mmd`.

Чтобы обновить SVG после изменения схемы, можно выполнить из папки `docs`:

```sh
npx --yes --package @mermaid-js/mermaid-cli@12.0.0 mmdc -i diagrams/components.mmd -o diagrams/components.svg -c diagrams/mermaid.config.json -b white --no-font-embed
```

Группы на схемах обозначают логические обязанности. Каждая группа не требует отдельного сервиса или контейнера.
