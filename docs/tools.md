# Начальные инструменты

[К содержанию](README.md)

Этот документ описывает начальный набор возможностей ядра для MVP с Telegram. Отдельный Ubuntu-компьютер подключается по SSH и описан ниже. Названия соответствуют инструментам MVP; параметры описаны в коде, здесь приводится их назначение.

Ядро предоставляет общие средства, необходимые для работы агента. Прикладные способы выполнения работы описываются в совместно сформированных skills. Отдельные встроенные интеграции с почтой, календарями и другими приложениями в начальный набор не закладываются.

## Codemode

Модель вызывает одну функцию `codemode` с полем `code`. Тело скрипта поддерживает
верхнеуровневые `await` и `return`. Все доступные в текущем ходе операции, в том
числе отправка ответов и обновление задач, вызываются как `tools.<имя>(аргументы)`.
`searchTools(запрос)` подбирает операции из доступного списка, а
`describeTool(имя)` возвращает описание и JSON-схему аргументов.

Скрипт выполняется в отдельном экземпляре QuickJS-NG в WebAssembly. Go
ограничивает память, время вычислений, размер выдачи и число вызовов.
Независимые чтения можно объединять через `Promise.all`. Действия записи и
операции с одним браузером идут по порядку. Ошибка инструмента отклоняет
promise, а `Promise.allSettled` позволяет обработать частичные результаты.
Модель получает итог `return` или `text()` и квитанции о действиях. В
инспекторе видны аргументы, результаты и попытки отдельных вызовов.

Temporal выполняет инструменты через их обычные Activities. При
восстановлении скрипт получает сохранённые результаты уже выполненных
вызовов. Неопределённый исход изменения нужно проверить перед повтором
действия. `store(ключ, значение)` и `load(ключ)` хранят небольшие JSON-значения
в пределах текущей сессии. Успешное завершение скрипта сохраняет изменения
этого состояния.

## Поиск и общение

| Инструмент | Назначение |
| --- | --- |
| `web_search` | При настроенном Yandex найти сведения в интернете, получить ссылки и краткие результаты. |
| `web_read` | Получить текст статической HTML-страницы или текстового файла по известному публичному URL. |
| `send_message` | Ответить, задать вопрос или отправить уведомление в доступный канал; приложить результат работы. |
| `send_rich_message` | Отправить ответ с нативными таблицами, формулами, сворачиваемыми секциями и другими rich-блоками. |
| `send_voice` | По явной просьбе ответить голосовым сообщением в текущем чате Telegram. |
| `report_progress` | Обновить одно временное сообщение статуса текущего интерактивного запроса и продолжить работу. |
| `send_group_message` | По прямой просьбе владельца из личного чата отправить текст в выбранную разрешённую группу или топик. |

В MVP `web_search` использует Yandex Search API, если заданы ключ и ID каталога. Эти настройки делают инструмент доступным в Codemode. При доступном браузере агент может искать через публичный поисковик и переходить по ссылкам из выдачи. Если поиск и браузер недоступны, агент читает известные публичные ссылки через `web_read` и при недостатке источников просит пользователя прислать ссылку. Автоматической замены API-провайдера нет. Общий интерфейс инструмента сохраняет возможность заменить провайдера в дальнейшем.

`web_read` не запускает JavaScript, не использует cookies браузера, теряет адреса ссылок и превращает заголовки, списки и таблицы в сплошной текст. Для чтения обычной статьи по известному адресу он подходит; для каталогов, поиска и переходов по ссылкам, таблиц и динамических страниц агенту следует выбирать браузер. Если нужные ссылки или содержимое потеряны при чтении, агент открывает страницу браузером и использует наблюдаемые ссылки вместо угадывания адресов. Успешный вызов может вернуть капчу или блокировку: агент должен проверить содержимое, при необходимости сменить источник и завершить исследование, когда данных достаточно для ответа, обозначив оставшиеся пробелы.

`send_message` используется и для ответа, и для уточнения. Если продолжение требует ответа пользователя, Workflow сохраняет ожидание. Адресат и область разговора проверяются приложением; инициатива не означает рассылку во все каналы.

По умолчанию агент использует `send_message`: обычные сообщения Telegram с форматированием Markdown и поддержкой цитирования выделенных фрагментов. Для нативных таблиц, формул, сворачиваемых секций и других rich-блоков доступен отдельный `send_rich_message` через Telegram `sendRichMessage`. Подробности и ограничения — в разделе «Формат ответов в Telegram» ниже.

## Виджеты Telegram

`send_widget` отправляет виджет только в текущий разрешённый личный чат Telegram.
`kind: "schedules"` и `task_ids` (1–4 ID из `task_find`) показывают пульт
активных или приостановленных повторяющихся задач. Включение переводит задачу в
`queued`, приостановка — в `paused`; расписание и результат сохраняются.
Уже завершённые, отменённые и разовые задачи через пульт не возобновляются.

Кнопки внутри виджета и inline-кнопки под подписью вызывают один серверный
обработчик без LLM. Он проверяет владельца, чат, реестр сообщения, разрешённые
задачи и версию задачи. Устаревшее нажатие не перезаписывает новое состояние.
Реестр хранится в PostgreSQL и переживает рестарт. Неизвестное сообщение получает
ответ с предложением открыть новый пульт. Для работы с клавиатуры есть команды
в меню бота: `/schedules [страница]` (по 4 задачи), `/pause ID`, `/resume ID`.
ID и команды видны в подписи. В группах и топиках команда сообщает, что виджеты
работают только в личке. `/new` и `/stop` сохраняют прежнее значение.

`kind: "html"` позволяет Альберту создавать собственные виджеты на лету:
написать HTML, inline CSS и JavaScript под конкретный запрос и сразу отправить
результат через `send_widget`. Например: сводка расходов с фильтром, сравнение
вариантов с вкладками, график или небольшая интерактивная карточка. Заготовленный
шаблон для этого не нужен. По просьбе «сделай виджет» агент отправляет готовый
виджет, а не описание или блок с его исходным кодом.

Визуальное качество входит в задачу по умолчанию: собственный inline CSS,
выразительная иерархия, системная типографика, согласованные отступы, аккуратная
палитра и оформленные состояния кнопок. Агент не должен ограничиваться голыми
заголовками, списком текста и стандартными браузерными кнопками, если пользователь
не просит простой вид. Дизайн выбирается под содержание, а не по одному шаблону
для всех случаев. Он должен сохранять читаемость в узком сообщении, в светлой и
тёмной теме, с длинными подписями и пустыми данными. Графики показывают только
реальные данные; оформление не должно добавлять вымышленные тренды.
Высота ограничена 600 пикселями, внутренней прокрутки нет: длинные списки
нужно сокращать или делить на локально переключаемые страницы.

JavaScript внутри виджета обрабатывает нажатия, переключает вкладки и фильтрует
данные локально. Для кнопок и текста подходят нативные стили Telegram; для
своего оформления — переменные `--tg-theme-*`, inline SVG и canvas. Поля ввода,
select и textarea не поддерживаются. Внешние ресурсы и сетевые запросы недоступны.
`allow_queries: false` отключает запросы к боту, сохраняя локальные взаимодействия;
произвольный HTML не получает разрешения управлять задачами.

Для последующих обновлений агент передаёт JSON в `chat_data` или `public_data`,
читает его через `TelegramWidget.chatData` / `publicData`, подписывается на
`chatDataChanged` / `publicDataChanged` через `TelegramWidget.onEvent` и вызывает
`TelegramWidget.ready()` после первого отображения. `edit_widget_data` обновляет
содержимое без повторной отправки; при смене HTML нужен новый виджет. Успешный
`send_widget` уже доставляет ответ — отдельное сообщение «виджет отправлен»
не требуется.

Лимиты: 1–32768 байт UTF-8 HTML,
не более 4096 байт после zlib level 9, до 1024 байт в каждом из `chat_data` и
`public_data`. NUL недопустим. Данные следует передавать в JSON-состоянии и
выводить через `textContent`, а не вставлять пользовательские строки в HTML.
Нужна содержательная текстовая `caption` до 1024 UTF-16 единиц. `width`
необязателен (минимум 200), `height` — 50–600 или автоматическая высота.

`edit_widget_data` принимает `message_id` из результата `send_widget` при
`fallback: false`, а также `chat_data` и/или `public_data`. Пропущенное поле сохраняется, пустая строка
очищает поле. Изменять можно только зарегистрированный HTML-виджет своего
чата. HTML после отправки неизменяем; состояние пульта меняет только сервер.
При `fallback: true` ID относится к обычному тексту; последующие обновления
следует отправлять текстом, а не через `edit_widget_data`.

При явном отказе `sendWidget` (400/404) отправляется обычный текст с теми же
inline-кнопками. Старые клиенты видят подпись и inline-кнопки даже при
неподдерживаемом содержимом. Сетевой сбой или 5xx могут означать неизвестный
результат доставки: автоматическая повторная отправка запрещена, чтобы не
создать дубликат. Результат инструмента содержит `message_id` и `fallback`;
отправка выполняется сразу и не завершает ход агента.

Запросы получают отдельный бюджет: до 4 секунд на действие, затем до 2 секунд
на `answerWidgetQuery`, затем отдельная попытка обновить отображение.
Виджет блокирует кнопки до ответа; Telegram дополнительно ограничивает запросы
пятью за пять секунд на пользователя. Shared widgets, inline-режим, форварды
и TON-операции не поддерживаются.

Явный отказ 429 сохраняет стадию отправки и `retry_after`: после паузы повторяется
только отвергнутый вызов (виджет или текстовый fallback). Такие ошибки не
кэшируются как окончательный результат инструмента. Каждая попытка отправки
сначала атомарно закрепляется в PostgreSQL, чтобы параллельные повторы не
создавали дубликаты. Для локального подсчёта сжатого размера используется
оригинальный алгоритм zlib, переведённый на Go (`modernc.org/libz`): стандартный
Go-компрессор даёт другой размер у границы 4096 байт. CGO не требуется.

Команды сохраняют текст подтверждения отдельно от действия. Если Telegram
отклонил подтверждение с 429, повторяется только отправка текста: уже выполненная
пауза или включение не повторяются и не отменяют более позднюю команду.
Ожидание `retry_after` не задерживает сообщения других чатов и запуск задач.

Подтверждённая отправка виджета учитывается при удалении временного сообщения
прогресса; если в том же ходе есть обычные сообщения, приложение сначала ждёт
доставки всех частей. Вызовы из хода HTTP API отклоняются до чтения кэша, даже
когда HTTP API и Telegram используют один личный разговор.

Платформа не поддерживает клавиатурный фокус, события клавиатуры, custom elements
или внешние библиотеки внутри виджета. Поэтому сочетания клавиш и UI SDK туда
добавить нельзя; альтернативный клавиатурный путь — команды бота. Ограничения:
[Telegram Widgets](https://core.telegram.org/bots/widgets),
[sendWidget](https://core.telegram.org/bots/api#sendwidget).

## Задачи

| Инструмент | Назначение |
| --- | --- |
| `task_create` | Зафиксировать поручение пользователя или самостоятельную задачу и обеспечить её запуск. |
| `task_find` | Найти задачи в доступной области по теме, состоянию или времени. |
| `task_read` | Получить актуальный статус, результаты, историю и дальнейшее продолжение. |

## История разговоров

### Отправка в группу из личного чата

Владелец может написать: «Отправь в группу Команда: встреча в 15:00». Агент выбирает точный `conversation_id` через `conversation_list`, при неоднозначном названии уточняет группу или топик и вызывает `send_group_message`. Затем отвечает владельцу через обычный `send_message` в личный чат. Дополнительное подтверждение при ясном поручении не требуется.

Инструмент доступен только в личном интерактивном разговоре владельца. Адресат должен быть известен приложению и входить в `TELEGRAM_ALLOWED_GROUP_IDS`. Группы, другие личные чаты, фоновая инициатива и задачи не могут отправлять сообщения этим инструментом. Права проверяются при исполнении, а Telegram-адаптер повторно проверяет разрешённого адресата при доставке.

Текст передаётся как Rich Markdown через устойчивую очередь outbox; лимит — 32000 байт UTF-8. Вложения этим инструментом пока не поддерживаются. В историю выбранной группы атомарно с записью outbox сохраняется только публичный текст с признаком запроса отправки. Личное поручение и личная переписка в группу не копируются. Повтор того же вызова инструмента не создаёт вторую запись в очереди и истории.

Результат `queued` означает постановку в очередь, а не подтверждение Telegram. При сетевом сбое с неизвестным исходом автоматическая повторная отправка запрещена общим механизмом доставки. Группа появляется в списке после первого принятого сообщения в ней; неизвестный адресат по произвольному ID не добавляется инструментом.

### Чтение истории

| Инструмент | Назначение |
| --- | --- |
| `conversation_list` | Список доступных разговоров: в личном чате владельца — также группы и топики; в остальных чатах — текущий разговор. |
| `conversation_history` | Прочитать или найти сообщения разных сессий доступного разговора, включая текст голосовых ответов. Поддерживает поиск по фрагменту текста и переход к более старым сообщениям. |

Чтение чужого `conversation_id` проверяется при исполнении. Группа не может запросить личную историю или соседнюю группу. Личный чат владельца может читать группы, сохраняя отправку ответов в личный чат. Подробности — в [правилах доступа к памяти](memory.md#личный-чат-как-общий-контекст-владельца).

## Диагностика собственных действий

`backup_status` доступен в личном чате владельца при настроенном `BACKUP_STATE_DIR`.
Он возвращает расписание, текущий этап, время обновления, последнюю проверенную
копию и известные даты из хостового файла состояния. Это локальный снимок,
не live-проверка S3. Устаревшие данные помечаются `unknown`; запуск, удаление
и восстановление через инструмент недоступны. Те же сведения автоматически
обновляются в контексте перед каждым вызовом модели. [Настройка резервирования](deployment.md#автоматические-копии-в-s3).

`logs_search` читает операционные события OpenAlbert из VictoriaLogs. Он доступен **в личном чате владельца и его запланированных задачах** (`TELEGRAM_OWNER_USER_ID`), включая ночной разбор логов. В группах, других личных чатах и инициативных запусках инструмент не предлагается; прямой вызов также отклоняется. Проверка прав выполняется до возврата сохранённого результата, поэтому кэш не обходит ограничение.

Примеры вопросов владельца: «Посмотри по логам, почему ты не ответил на последний запрос», «Почему поиск остановился вчера около 18:00?», «Был ли ответ действительно доставлен?». Если неизвестна сессия, агент сначала находит исходное обращение через `conversation_history`. По умолчанию поиск относится к текущему личному разговору; владелец может выбрать известную группу через `conversation_id` из `conversation_list`. Чужие личные разговоры остаются недоступны.

Инструмент возвращает сводку по операциям, исходам и кодам ошибок, затем последние события с временем, длительностью, номерами попыток, статусом доставки, `trace_id` и ссылкой в инспектор. Фильтры точные: `session_id`, `turn_id`, `operation`, `tool`, `result`, `error_code`. `since` и `until` задаются в RFC3339 с часовым поясом; правая граница исключается. По умолчанию выбирается последний час, окно ограничено сутками, число записей — 20 по умолчанию и не более 50. При обрезке результата агент должен сузить окно или идентификатор; `summary_truncated` отдельно отмечает неполную сводку.

Это чтение метаданных `service=openalbert` в разрешённой области. Произвольный LogsQL, адрес сервера, shell-команды, удаление логов и изменение настроек не принимаются. Тексты переписки, полные запросы к модели и результаты инструментов через этот инструмент не читаются. Логи могут запаздывать, теряться и удаляться по retention; отсутствие записи не доказывает отсутствие действия. `queued` не подтверждает доставку, а успешная Activity не гарантирует успех действия. Тексты логов — данные, а не инструкции. Агенту предписано отделять установленные факты от предположений и не заявлять об исправлении по одному чтению журнала.

Доступ включается настройкой `VICTORIALOGS_URL`. Compose по умолчанию использует внутренний `http://victorialogs:9428`, а явное пустое значение отключает инструмент. Для запуска через `go run` адрес задаётся явно, например `http://localhost:9428`. Лимиты ответа и таймауты действуют независимо от аргументов модели.

| `memory_read` | Прочитать запись и её происхождение; для результата из группы указать её `conversation_id`. |

| `participant_update` | Сохранить или исправить личный факт в исходной группе, указав автора, сообщение и точную цитату; удалить по просьбе самого участника. |

Изменения сохраняются на хосте и применяются со следующего обращения. Публикация активной версии skill требует ручного применения согласованной правки. Общего shell-доступа к основному контейнеру нет; tools памяти ограничены своим хранилищем.

## Общий путь исполнения

LLM выбирает инструмент, Workflow запускает Activity, адаптер выполняет операцию и сохраняет результат. Вывод возвращается модели либо используется для ожидания следующего события. Ошибка инструмента также может быть возвращена модели для выбора другого действия; исчерпание допустимых попыток приводит к сохранению состояния и остановке текущей работы.

Перед выполнением приложение проверяет область данных и доступность действия. Для внешних изменений правила повторов зависят от операции. Уведомление пользователя о неопределённом результате предпочтительнее необоснованного сообщения об успехе.

Skill может научить пользоваться программой через эти средства. Появление нового встроенного tool остаётся изменением приложения; сам агент его автоматически не устанавливает.

## Удалённый компьютер

Пользователь предоставляет Linux-компьютер с SSH, Python 3.9+ и Bash. Ядро
подключается по SSH с настроенным пользователем, паролем или ключом. Исполнитель
устанавливается и обновляется автоматически в домашнем каталоге; `sudo` не требуется.
Права команд определяются SSH-пользователем. Проверка ключа сервера отключена.
Инструменты
доступны только в личном чате владельца и его активных запланированных задачах;
в группах, других личных чатах и инициативных запусках они отсутствуют. Права
проверяются до исполнения и до возврата сохранённого результата.

| Инструмент | Назначение |
| --- | --- |
| `computer_exec` | Запустить Bash-команду на настроенной машине. |
| `computer_execution_status` | Прочитать состояние операции и следующую часть stdout/stderr. |
| `computer_execution_cancel` | Запросить остановку известной операции, включая ожидающую в очереди. |
| `computer_upload` | Перенести артефакт текущего разговора на компьютер. |
| `computer_download` | Сохранить файл компьютера как артефакт для чтения или отправки. |

Пример: вложение Telegram уже имеет `artifact_id`. Агент вызывает `computer_upload`
с этим ID и путём `/workspace/project/input.csv`, затем `computer_exec` с командой
и `cwd=/workspace/project`. После подтверждённого завершения он сохраняет результат
через `computer_download` и отправляет его обычным `send_message` с `artifact_id`.
Двоичные данные передаются адаптером по SSH без включения в контекст модели.
Специального постоянно работающего сервиса исполнения нет: `openalbert-computer`
является небольшим CLI и запускает отдельный процесс наблюдения за командой.

### Исполнение и восстановление

По умолчанию команда выполняется в `~/.openalbert/workspace` удалённого пользователя,
имеет таймаут 300 секунд и ждёт
результат до 1 секунды. `timeout_seconds` допускает 1–86400, `wait_seconds` — 0–5.
Оставшееся выполнение продолжается независимо от SSH и от сессии диалога. Команды
на общей машине выполняются последовательно; остальные получают `queued`. Это
согласует команды, но не делает последовательность нескольких вызовов атомарной:
проектам нужны отдельные каталоги. Передача файлов может выполняться между командами.

Приложение регистрирует `execution_id` до отправки. На компьютере неизменяемый
запрос сохраняется до запуска процесса. Повтор той же Activity проверяет тот же ID;
команда не запускается заново. Другой запрос с тем же ID отклоняется.

![Удалённое действие и проверка результата при потере связи](diagrams/computer-execution.svg)

[Исходник схемы](diagrams/computer-execution.mmd)

Состояния: `queued`, `running`, `completed`, `failed`, `cancelled`, `timed_out`,
`unknown`. `exit_code` присутствует, когда фактический код завершения известен.
Потеря SSH не останавливает процесс: агент проверяет тот же `execution_id`.
Перезапуск компьютера останавливает его процессы; если финального результата нет,
операция становится `unknown` и автоматически не перезапускается. Отсутствующая
запись также не доказывает, что команда не выполнялась. Записи операций не защищены
от изменений самим пользователем с `sudo` и не являются независимым аудитом.

Вывод сохраняется до 1 МиБ на stdout и отдельно на stderr; лишние байты отбрасываются.
Один ответ содержит до 2048 байт каждого потока. Следующее чтение использует
возвращённые `stdout_offset` и `stderr_offset`; `has_more` означает оставшийся
сохранённый вывод, `output_truncated` — превышение общего лимита. Большие результаты
лучше писать в файл. Для долгой работы агент сохраняет ID в результате задачи и
назначает следующую проверку, вместо постоянного опроса в одном запуске.

Отмена ставит запрос остановки. Наблюдатель отправляет SIGTERM группе процессов,
затем SIGKILL. Это best effort: отдельные сессии и привилегированные процессы могут
избежать остановки, произведённые изменения не откатываются. Отмена/пауза задачи
сама по себе не останавливает уже переданную команду: перед этим агент должен
вызвать `computer_execution_cancel`. Неактивная задача не может запускать новые
команды или обмен файлами; читать статус и отменять известную операцию можно.

### Файлы и настройки

Перенос ограничен обычными файлами до 20 МиБ в `/workspace` и домашнем каталоге
пользователя. Путь должен быть абсолютным; выход через симлинк за эти каталоги
отклоняется. Загрузка не перезаписывает отличающиеся файлы: для новой версии
нужно выбрать новый путь. Повтор загрузки одинаковых байтов допустим.
Ограничение путей относится к переносу файлов; `sudo` в команде даёт системный
доступ внутри компьютера.

Рабочий каталог по умолчанию — `~/.openalbert/workspace`, записи операций —
`~/.openalbert/executions`. Версии исполнителя сохраняются в `~/.openalbert/runners`
по SHA-256 кода, встроенного в backend. Новая версия устанавливается перед запросом,
активные и ожидающие команды продолжают использовать свою версию; записи и блокировка
общие. ОС, программы и данные обслуживает пользователь. Для необязательного
Docker-шаблона системные изменения теряются при пересоздании контейнера.
Параметры подключения, подготовка, обновление и проверка — в
[руководстве компьютера](computer.md).

## Формат ответов в Telegram

Промежуточные этапы длительной работы сообщаются через `report_progress`, а не через `send_message` или `send_rich_message`. В группах и групповых топиках прогресс сохраняется только внутри приложения; статусные сообщения не отправляются. В личных Telegram-чатах это видимый пользователю обычный текст до 600 символов: фактические действия, следующий шаг или препятствие, без внутреннего рассуждения и вымышленных процентов. Инструмент не создаёт отдельное сообщение на каждый вызов: приложение хранит последнее состояние, показывает его с задержкой и редактирует одно сообщение. Оно удаляется после успешной доставки всего ответа; при ошибке или остановке остаётся с итоговым статусом. Точные интервалы и правила восстановления описаны в [разделе сессий](sessions.md).

`send_message` или `send_rich_message` вызывается явно для отправки ответа, вопроса, уведомления или запрошенного артефакта пользователю. Оба инструмента используют устойчивую очередь, одинаковые проверки области разговора, вложений и уведомлений; успешная постановка ответа в очередь не завершает ход. Модель продолжает работать и отправлять остальные запрошенные сообщения или артефакты, затем завершает ход обычным финальным ответом без вызовов инструментов. Обычный финальный текст модели остаётся в истории запуска: автоматического преобразования в сообщение нет. Если сообщать нечего, агент завершает запуск без вызова инструмента. Пустые, пробельные и невидимые сообщения-заглушки запрещены инструкцией; обязательной отправки для завершения запуска нет.

`send_message` — выбор по умолчанию для диалога, объяснений, напоминаний и кода. Markdown преобразуется в обычный текст и Telegram entities: заголовки, выделения, ссылки, списки и код сохраняют оформление. При необходимости ответ делится на части до 4096 единиц UTF-16, без разрыва суррогатных пар и с сохранением entities. Каждая часть имеет отдельную устойчивую запись outbox и состояние доставки, поэтому повтор после ограничения частоты не дублирует подтверждённые части. Для запросов из настольного клиента исходный Markdown сохраняется без разбиения.

`send_rich_message` используется, когда для содержимого полезны нативные таблицы, формулы, сворачиваемые секции или другие rich-блоки, либо пользователь явно просит rich-оформление. Исходный Rich Markdown сохраняется в outbox и передаётся Telegram как `rich_message.markdown` через `sendRichMessage`, без разбиения по 4096. Telegram ограничивает сообщение 500 блоками, 20 колонками таблицы и 16 уровнями вложенности. Выделенная цитата rich-сообщения может не доходить до бота из-за текущего ограничения Bot API; обычная отправка остаётся предпочтительной для обсуждения отдельных фрагментов.

`send_message` и `send_rich_message` принимают до 32000 байт UTF-8 и не требуют MarkdownV2 escaping. Длинные документы следует сохранять артефактом. Служебные сообщения и ранее поставленные в очередь исходные rich-ответы сохраняют прежний способ доставки.

`send_voice` принимает до 1000 символов обычного текста и ставит голосовой ответ в очередь. Он доступен в текущем Telegram-диалоге с входящим сообщением. Приложение само отправляет текст при проблеме с голосовой доставкой. Настройки описаны в [руководстве по голосовым сообщениям](speech.md#голосовые-ответы-через-piper).

Чтобы отправить изображение или файл с описанием одним сообщением, агент передаёт `text` и `artifact_id` в одном вызове `send_message` или `send_rich_message`. Короткое описание преобразуется из Markdown в текст подписи и `caption_entities` с форматированием и ссылками. Проверка длины использует консервативный предел 1024 единицы UTF-16 после преобразования. Подпись и вложение сохраняются одной записью outbox и отправляются одним запросом. Если описание длиннее, текст отправляется отдельно в формате выбранного инструмента, а вложение — без подписи, без обрезания описания.

PNG/JPEG отправляются через `sendPhoto`, если размер не больше 10 МиБ, сумма ширины и высоты не превышает 10000 пикселей, а отношение сторон не больше 20. Формат и размеры проверяются по содержимому. Остальные вложения отправляются через `sendDocument`, также с подписью, если она помещается. После ошибки фото не пересылается автоматически файлом: неопределённый результат остаётся одной доставкой со статусом `unknown`, а явный лимит частоты разрешает повтор всего сообщения.

Записи outbox с готовыми entities отправляются через обычный `sendMessage` без повторного разбора Markdown. Исходные rich-записи продолжают использовать `sendRichMessage`. Ошибка доставки не вызывает автоматическое переключение между форматами: неизвестный исход остаётся в состоянии `unknown` для защиты от дубликатов.

См. [формат Rich Messages и ограничения Telegram](https://core.telegram.org/bots/api#rich-messages).
