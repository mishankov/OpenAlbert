# Запуск и разработка MVP

MVP работает через Telegram и нативный клиент macOS. Backend написан на Go; модель и OpenAI-совместимый endpoint выбираются настройками запуска. Docker Compose поднимает OpenAlbert, PostgreSQL, Temporal и его Web UI, MinIO для вложений и VictoriaLogs. Отдельный Ubuntu Computer box доступен по SSH. Подключение desktop-клиента описано в [desktop.md](desktop.md).

Этот документ описывает локальную разработку через `compose.local.yaml`: OpenAlbert, STT,
log-gateway, MinIO и инициализатор бакета собираются из исходников. Установка готовых
образов из GHCR и локальная публикация описаны в [руководстве публикации](deployment.md).
`compose.yaml` запускается отдельно и не требует сборки на сервере.

Полный набор проверок и сборок запускается через [Task](local-checks.md):
`task check`, `task test`, `task images`, `task verify`.

## Первый запуск

После обновления приложения владелец может попросить OpenAlbert разобрать собственную ошибку по логам через `logs_search`. Compose передаёт `VICTORIALOGS_URL=http://victorialogs:9428`, если переменная не задана. `VICTORIALOGS_URL=` отключает инструмент; при запуске без Docker адрес нужно задать явно. Инструмент доступен в личном чате и запланированных задачах владельца, заданного `TELEGRAM_OWNER_USER_ID` (по умолчанию первый разрешённый пользователь), и не требует отдельного секрета. Инициативные проверки и группы доступа не имеют. Недоступность VictoriaLogs возвращает ошибку инструмента, сохраняя работу самого OpenAlbert.

Нужны Docker Engine с Compose v2 и свободные локальные порты 5432, 7233, 8080, 8233, 9000, 9001, 9428 и 9429. Если 5432 занят, задай `POSTGRES_PORT` в `.env` (например, `15432`) и поменяй порт в локальном `DATABASE_URL`; внутри Compose PostgreSQL продолжает слушать 5432.

```sh
cp .env.example .env
```

Заполни `.env`: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_ALLOWED_USER_IDS`, `LLM_API_KEY`, `LLM_MODEL`. Для старта Яндекс не требуется: оставь `YANDEX_API_KEY` и `YANDEX_FOLDER_ID` пустыми. Без них агент читает публичные ссылки через `web_read`, а `web_search` отсутствует в доступных инструментах. Для подключения поиска позже заполни обе настройки. Файл игнорируется Git. После этого:

```sh
docker compose -f compose.local.yaml up -d --build
```

В `TELEGRAM_ALLOWED_USER_IDS` указываются числовые Telegram ID разрешённых пользователей через запятую. Пустой список запрещает запуск. По умолчанию бот принимает только личные сообщения от этих пользователей. Для групп нужно дополнительно указать отрицательные ID групп в `TELEGRAM_ALLOWED_GROUP_IDS`; в разрешённых группах принимаются сообщения всех обычных участников, доставленные Telegram. Список `TELEGRAM_ALLOWED_USER_IDS` ограничивает личные чаты. Группы видят только свой контекст. Личный чат владельца может читать сохранённые групповые обсуждения через инструменты истории и памяти; обратный доступ запрещён кодом.

Инспектор сессий: `http://localhost:8080/inspect/` ([возможности и ограничения](inspector.md)). Health endpoint доступен на `http://localhost:8080/healthz`. VictoriaLogs: `http://localhost:9428/select/vmui/`. Консоль MinIO: `http://localhost:9001`. Temporal UI: `http://localhost:8233` (без логина и пароля, доступ только с этой машины). Сервисы опубликованы только на loopback-интерфейсе; для доступа из другой машины потребуется отдельная настройка аутентификации и TLS.

Не запускай два экземпляра Telegram poller с одним токеном. Для смены модели измени `LLM_MODEL` и при необходимости `LLM_BASE_URL`/`LLM_API_KEY`, затем пересоздай приложение:

```sh
docker compose -f compose.local.yaml up -d --force-recreate openalbert
```

Для OpenCode Go с Chat Completions используется `LLM_BASE_URL=https://opencode.ai/inference/go/openai/v1`, а `LLM_MODEL` содержит ID модели без префикса провайдера, например `deepseek-v4.1-flash`. Адаптер представляется как `OpenAlbert/0.1` и передаёт стабильный `x-opencode-session` для разговора, включая анализ сессий. Значение заголовка — непрозрачный хеш, не Telegram ID. Эти требования описаны в [документации OpenCode Go](https://opencode.ai/v2/docs/console/go/).

Для моделей с ID `deepseek-*` (в том числе после префикса провайдера через `/`) адаптер возвращает сохранённое служебное поле `reasoning_content` во всех сообщениях ассистента, включая текстовые ответы и пустое значение. Это требуется для продолжения работы с инструментами в thinking mode; потеря поля приводит к HTTP 400. Служебное поле передаётся отдельно от текста ответа и не добавляется к пользовательским сообщениям или результатам инструментов. Для остальных моделей адаптер это поле не отправляет. Контракт описан в [документации DeepSeek](https://api-docs.deepseek.com/guides/thinking_mode/#tool-calls).

Chromium установлен в образ OpenAlbert и запускается по необходимости. Для запуска Go-бинарника вне Docker установи Chromium или задай `BROWSER_EXECUTABLE`. Поддерживаются публичные сайты без входа в аккаунты. Ограничения контейнера и sandbox описаны в [разделе браузера](browser.md).

## Как смотреть исполнение в Temporal UI

Открой [Temporal UI](http://localhost:8233). Логин и пароль не нужны: локальная установка работает с `TEMPORAL_AUTH_ENABLED=false` и опубликована только на loopback. UI подключается к `temporal:7233` внутри Compose; браузеру этот служебный адрес не нужен. Смена локального порта задаётся через `TEMPORAL_UI_HOST_PORT` в `.env` с последующим `docker compose -f compose.local.yaml up -d temporal-ui`.

В namespace из `TEMPORAL_NAMESPACE` (по умолчанию `default`) открой **Workflows**. Здесь видны исполняемые и завершённые workflows, их статусы и время запуска. В карточке workflow история показывает вызовы Activities, результаты, ошибки, повторные попытки и таймеры. Длительное ожидание таймера у задачи, назначенной на будущее, нормально: процесс не вызывает модель всё это время.

Поручения представлены `TaskWorkflow`, разговорные сессии — `SessionWorkflow`, анализ закрытых сессий — `AnalysisWorkflow`, периодическая инициатива — `InitiativeWorkflow`. Для поиска конкретной задачи используй Workflow ID вида `task/<id задачи>`. Статус Running у Workflow означает, что он ещё жив; он может сейчас ждать таймер или сообщение. Текущее содержимое пользовательской задачи остаётся в PostgreSQL, а Temporal UI показывает её исполнение.

Сервис UI закреплён на образе `temporalio/ui:2.54.1`, дожидается здорового Temporal, проверяет доступность API namespaces и отправляет логи общим Docker logging driver в VictoriaLogs с `service:temporal-ui`. Собственных постоянных томов UI не требует. Подключение UI не меняет задачи или историю агента. Настройки образа описаны в [официальном справочнике Temporal](https://docs.temporal.io/references/web-ui-environment-variables).

HTTP-журнал UI сохраняется полностью; ссылка «Логи» (`Alt+L`) в инспекторе открывает фильтр без быстрых успешных запросов UI. Gateway выделяет статус, метод, путь без query-параметров и длительность HTTP-запроса. Для полной истории используй `service:temporal-ui`.

## Настройки запуска

Полный пример находится в `.env.example`. Compose задаёт адреса инфраструктуры внутри своей сети автоматически; настройки ниже также используются при запуске бинарника вне Docker.

| Настройка | Назначение |
| --- | --- |
| `DATABASE_URL` | PostgreSQL URL приложения |
| `TEMPORAL_UI_HOST_PORT` | Локальный порт Temporal UI, по умолчанию `8233`; вход без пароля, опубликован только на `127.0.0.1` |
| `TEMPORAL_ADDRESS`, `TEMPORAL_NAMESPACE`, `TEMPORAL_TASK_QUEUE` | Адрес Temporal, namespace и очередь workers |
| `TELEGRAM_BASE_URL` | Необязательный корень Bot API server; пусто — официальный Telegram endpoint |
| `TELEGRAM_BOT_TOKEN` | Токен Telegram Bot API |
| `TELEGRAM_ALLOWED_USER_IDS` | Обязательный список разрешённых пользователей |
| `TELEGRAM_OWNER_USER_ID` | Владелец, чей личный чат может читать историю и память групп. ID должен входить в список разрешённых; по умолчанию первый ID в нём. |
| `TELEGRAM_ALLOWED_GROUP_IDS` | Разрешённые группы; пусто — только личные чаты |
| `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL` | OpenAI-совместимый endpoint, ключ и фиксированная модель запуска |
| `STT_BASE_URL`, `STT_MODEL`, `STT_REVISION`, `STT_API_KEY` | Независимый файловый STT; Compose подключает контейнер Nemotron. [Настройки и активация](speech.md). |
| `YANDEX_SEARCH_URL` | Необязательный endpoint поиска для тестового HTTP-сервера или прокси; пусто — Yandex API v2 |
| `YANDEX_API_KEY`, `YANDEX_FOLDER_ID` | Необязательный доступ к Yandex Search API; обе настройки заполняются вместе или остаются пустыми |
| `KNOWLEDGE_DIR` | Постоянный каталог skills и памяти |
| `BROWSER_ENABLED` | Браузерные инструменты, по умолчанию `true`; образ содержит Chromium |
| `BROWSER_EXECUTABLE` | Необязательный путь к Chromium; пусто — поиск в PATH |
| `BROWSER_NO_SANDBOX` | Compose: `true` для текущего Docker Desktop; вне Docker по умолчанию `false` |
| `SOUL_FILE` | Необязательный отдельный файл характера; по умолчанию `SOUL.md` в `KNOWLEDGE_DIR` |
| `SESSION_IDLE_TIMEOUT` | Время без новых сообщений до закрытия сессии, по умолчанию `30m` |
| `MAX_AGENT_STEPS` | Максимум исследовательских шагов одного агентского запуска, по умолчанию `100`; для интерактивного запроса после лимита разрешён ещё один завершающий вызов модели только с `send_message`. Значение фиксируется при создании Workflow |
| `TASK_MIN_INTERVAL` | Минимальный период повторяющихся задач, по умолчанию `5m` |
| `INITIATIVE_INTERVAL` | Период фоновой инициативы, по умолчанию `30m`; `0` отключает её |
| `HTTP_ADDR` | Listen-адрес HTTP-сервера (health endpoint и инспектор), по умолчанию `:8080` |
| `S3_ENDPOINT`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`, `S3_BUCKET`, `S3_SECURE` | S3-совместимое хранилище; endpoint указывается без схемы |
| `POSTGRES_PORT` | Локальный опубликованный порт PostgreSQL, по умолчанию `5432` |
| `POSTGRES_PASSWORD` | Пароль PostgreSQL для Compose; при локальном запуске должен совпадать с `DATABASE_URL` |
| `DOCKER_LOGS_GATEWAY_URL` | Адрес приёмника Docker-логов со стороны daemon, по умолчанию `http://127.0.0.1:9429` |
| `TEMPORAL_LOG_LEVEL` | Уровень логов сервера Temporal; `warn` по умолчанию, `info` для подробной диагностики |

Значения длительностей используют синтаксис Go: `30s`, `5m`, `6h`. По умолчанию SOUL хранится в `container_data/knowledge/SOUL.md` на хосте и `/data/knowledge/SOUL.md` в Compose. При запуске вне Docker каталог по умолчанию тот же: `./container_data/knowledge`. `SOUL_FILE` позволяет указать другой существующий файл; для работы `soul_update` файл и его каталог должны быть доступны процессу на запись. Публикация skills выполняется человеком после совместного обсуждения; агент сохраняет предложения отдельно.

Интервал инициативы фиксируется во входных параметрах `InitiativeWorkflow`. Для изменения уже запущенной инициативы после правки `INITIATIVE_INTERVAL` пересоздай приложение и отмени прежний `initiative/...` workflow через Temporal UI. Диспетчер создаст новый запуск с новым интервалом; первый таймер отсчитывается от его запуска. Пользовательские `TaskWorkflow` для этого перезапускать не нужно.

## Как задать характер

Попроси бота в личном диалоге изменить имя или характер, например: «Теперь тебя зовут Атлас. Обнови SOUL.md». Агент прочитает актуальный текст и сохранит точечную правку. Можно также открыть `container_data/knowledge/SOUL.md` в редакторе и описать манеру общения, инициативу и принципы. При первом запуске отсутствующий SOUL создаётся из встроенного шаблона `internal/knowledge/templates/SOUL.md`.

Файл перечитывается при подготовке следующего запроса или фонового запуска. Пересобирать контейнер после правок не нужно. Уже выполняющийся шаг использует собранный ранее контекст. Изменять SOUL через инструмент можно только в личном интерактивном диалоге; в группах, задачах и проверках инициативы запись запрещена. Не редактируй файл вручную одновременно с выполняющейся правкой агента.

Память и опубликованные skills находятся в `container_data/knowledge/` в корне репозитория. Compose подключает этот каталог к `/data/knowledge` с правом записи. Его можно открыть обычным файловым менеджером или редактором; содержимое исключено из Git и Docker build context. Профиль разговора лежит в `container_data/knowledge/scopes/<хеш разговора>/USER.md`, заметки — в соседнем каталоге `memories/`, профили участников групп — в `participants/<Telegram ID>/`, навыки — в `container_data/knowledge/skills/`. На Linux каталог должен быть доступен пользователю контейнера с UID/GID `10001:10001`; при необходимости создай его заранее и назначь владельца. SOUL включён в тот же каталог и резервируется вместе с памятью.

## Работа с Go локально

Нужен Go 1.26. Для запуска инфраструктуры без бота и внешних ключей:

```sh
docker compose -f compose.local.yaml up -d --build log-gateway postgres temporal victorialogs minio minio-init
```

Для локального запуска `.env` нужно загрузить в окружение процесса; само приложение не читает dotenv-файлы. Для примера `.env.example` с простыми значениями подходит:

```sh
set -a
. ./.env
set +a
go run ./cmd/openalbert
```

Произвольные токены и пароли в shell-файле требуют корректного quoting; удобнее передать переменные средствами IDE или менеджера секретов. Секреты не передаются через аргументы командной строки и не выводятся в сообщения об ошибках конфигурации.

```sh
go test ./...
go test -race ./...
go vet ./...
docker compose -f compose.local.yaml config -q
python3 deploy/check-compose.py
```

Проверки интеграций используют локальные HTTP-имитаторы, чтобы не расходовать деньги и не отправлять сообщения настоящим пользователям. Проверка с реальными ключами — отдельный запуск владельца; успешные локальные проверки не доказывают доступность выбранного провайдера или поддержку конкретной моделью tool calls и изображений.

Для проверки инструкций поиска на выбранной модели есть отдельная opt-in оценка. Передай `LLM_BASE_URL`, `LLM_API_KEY` и `LLM_MODEL` через окружение процесса теста и запусти:

```sh
OPENALBERT_LIVE_RETRIEVAL_EVAL=1 go test ./internal/agent -run '^TestLiveRetrievalPrompts$' -v -count=1
```

Она вызывает реальную модель с рабочими инструкциями и описаниями инструментов, но использует временную память, задачи и outbox без доставки в Telegram. Проверяет использование готового профиля, поиск конкретного факта, восстановление после несовпадения написания названия, обзор последних записей и поиск расписания в задачах. В обычном `go test` оценка пропускается; результат зависит от выбранной модели и не гарантирует успех всех будущих запросов.

Отдельная оценка проверяет решение модели об отправке: прямой вопрос, приветствие и запрос статуса должны привести к явному `send_message`; просьба не отвечать, фоновая задача без новых данных и инициатива без новостей — завершиться без доставки. Она также использует изолированную память и outbox, реальные сообщения в Telegram не отправляет. С теми же `LLM_*`:

```sh
OPENALBERT_LIVE_DELIVERY_EVAL=1 go test ./internal/agent -run '^TestLiveDeliveryPrompts$' -v -count=1
```

## Сквозная проверка контейнера

После сборки образа и запуска инфраструктуры можно воспроизвести реальный путь сообщения без внешних ключей:

```sh
docker compose -f compose.local.yaml build openalbert
python3 deploy/mvp-smoke.py
# Проверка запуска и работы без Яндекса:
python3 deploy/mvp-smoke.py --without-search
```

Требуется Python 3 и свободный порт 18089. Harness поднимает локальные имитаторы Telegram, OpenAI-совместимого API и Yandex, затем запускает настоящий контейнер OpenAlbert через временный Compose override. В Docker Desktop контейнер обращается к ним через `host.docker.internal`; для другого Docker Engine передай `--host-address` с доступным из контейнера адресом хоста.

С флагом `--with-browser` smoke дополнительно открывает публичный `https://example.com` в настоящем Chromium, сохраняет скриншот через S3 и проверяет освобождение процесса после закрытия сессии. Telegram и модель остаются локальными имитациями.

Проверяются приём сообщения, агентский цикл в Temporal, поиск, автоматическое сохранение памяти, длительная задача, две доставки через outbox, закрытие сессий и анализ, сохранение текстового вложения в S3, wide events в VictoriaLogs. После перезапуска приложения тот же Telegram update воспроизводится повторно: модель и отправка не должны повториться, память должна сохраниться.

Проверка использует отдельные PostgreSQL database, bucket и volume, затем удаляет их и тестовый контейнер приложения. Работающая инфраструктура и сайт документации сохраняются. Если OpenAlbert уже работает, harness завершится без замены контейнера; сначала останови свой экземпляр. История тестовых workflows и диагностические события остаются в Temporal и VictoriaLogs до истечения retention. Для обычного запуска после smoke снова выполни `docker compose -f compose.local.yaml up -d openalbert` с собственными настройками.

## Логирование

Собственные операции OpenAlbert завершаются одним JSON wide event: идентификатор операции, контекст, результат, длительность, счётчики. Секреты, полные сообщения, prompts, содержимое файлов и сырые ошибки провайдеров не логируются. Такой подход основан на [Logging Sucks Бориса Тейна](https://loggingsucks.com/).

Все контейнеры используют Docker-драйвер `splunk` и отправляют JSON в `log-gateway`. Этот сервис снимает обёртку Docker и передаёт JSON Lines в VictoriaLogs. В результате VMUI получает короткие поля `service`, `container`, `project`, `level`, `operation`, `turn_id`, а сообщения начинаются с `[openalbert]`, `[postgres]` или другого источника. Фильтры: `service:openalbert`, `service:temporal`, `service:postgres`, `service:openalbert result:error`. Служебные INFO-события Temporal по умолчанию отключены настройкой `TEMPORAL_LOG_LEVEL=warn`.

Драйвер выполняется в Docker daemon, поэтому hostname Compose-сети ему не подходит. Published port приёмника доступен по `DOCKER_LOGS_GATEWAY_URL`; прежняя переменная `DOCKER_LOGS_URL` больше не используется. Для удалённого daemon адрес задаётся относительно его машины. Интерфейс VictoriaLogs остаётся на `http://127.0.0.1:9428/select/vmui`. Счётчики доставки шлюза: `http://127.0.0.1:9429/healthz`. Настройки и ограничения подробно описаны в [логировании](observability.md).

Для разрыва стартовой зависимости VictoriaLogs от собственных логов отключена синхронная проверка соединения. Неблокирующий буфер драйвера ограничен `4m`; у Splunk-драйвера также есть собственный ограниченный буфер повторных отправок. Приложение продолжает работать при недоступности сборщика; при переполнении или перезапуске daemon часть логов может потеряться. Это не архив с гарантированной доставкой. Операционное состояние хранится в PostgreSQL и Temporal, а не восстанавливается по логам. [Настройки и ограничения драйвера](https://docs.docker.com/engine/logging/drivers/splunk/).

```sh
docker compose -f compose.local.yaml logs --tail=100 openalbert
curl -fsSG http://localhost:9428/select/logsql/query --data-urlencode 'query=*' --data-urlencode 'limit=10'
```

## Границы первой версии

Запускается одна реплика приложения: Telegram poller, доставка outbox и workers работают в одном процессе. Входные данные MVP — текст, фотографии, текстовые документы и голосовые; сохранённые изображения можно повторно прочитать инструментом работы с артефактами. Голос распознаётся независимым STT endpoint, в Compose — CPU-контейнером Nemotron. Первый запуск STT загружает проверенные веса; существующий MVP активируется отдельно по [инструкции](speech.md). PDF и видео сохраняются как артефакты; извлечение содержимого из них пока не реализовано.

Поиск памяти лексический. Публикация skills требует ручного просмотра и принятия предложения; агент не меняет собственный характер. HTTP-интеграции проверены локальными имитаторами, включая сквозной запуск настоящего контейнера; реальные внешние ключи в проверках не использовались.

### Проверка чтения логов

HTTP-контракт адаптера можно проверить на отдельном одноразовом VictoriaLogs:

```sh
OPENALBERT_TEST_VICTORIALOGS_URL=http://127.0.0.1:19428 go test -count=1 -run '^TestVictoriaLogsContract$' -v ./internal/integrations
```

Тест записывает собственные фикстуры и проверяет точные фильтры, временные границы, сводку и изоляцию разговоров. Адрес должен вести в отдельный тестовый экземпляр. Обычный `go test -race ./...` также проверяет запрет вызовов из групп и других личных чатов, ограничение кэша правами владельца, размер ответа, отмену, перенаправления и Workflow «прочитать диагностику → ответить владельцу» на имитаторе модели.

## Данные, остановка и резервная копия

Все постоянные данные Compose находятся в `container_data/` в корне репозитория и подключаются через bind mounts. Каталог исключён из Git и Docker build context.

| Каталог на хосте | Содержимое | Путь в контейнере |
| --- | --- | --- |
| `container_data/postgres/` | Базы приложения и Temporal | `/var/lib/postgresql/data` |
| `container_data/minio/` | Вложения и результаты | `/data` |
| `container_data/victorialogs/` | Логи всех сервисов | `/storage` |
| `container_data/knowledge/` | SOUL, профили, память и skills | `/data/knowledge` |

`docker compose -f compose.local.yaml down`, включая вариант `-v`, не удаляет эти каталоги. Не удаляй `container_data/`, если данные нужно сохранить. Скрипты и настройки инфраструктуры подключаются из `deploy/` только для чтения. Изменяемый характер хранится вместе с памятью.

Для согласованной файловой резервной копии останови все сервисы, скопируй `container_data/` с сохранением владельцев и прав, а также настройки `.env`. После копирования снова запусти сервисы. Файлы PostgreSQL можно копировать только после его корректной остановки; для переносимой копии баз дополнительно используй `pg_dumpall`. При восстановлении файлов PostgreSQL нужна совместимая версия сервера. После восстановления все базы должны соответствовать одной версии приложения; Temporal использует свои схемы, приложение — свои миграции.

```sh
# Необязательная переносимая копия баз перед полной остановкой:
docker compose -f compose.local.yaml stop openalbert temporal
docker compose -f compose.local.yaml exec -T postgres pg_dumpall -U openalbert > /safe/backup/openalbert.sql
docker compose -f compose.local.yaml stop
# Скопируй container_data/ и .env с сохранением прав.
docker compose -f compose.local.yaml up -d
```

При миграции текущей установки данные перенесены после остановки сервисов и проверены по контрольным суммам и числу записей в таблицах. Прежние именованные Docker-тома удалены; постоянные данные находятся только в `container_data/`.

Каталог `/safe/backup` в примере нужно создать заранее вне репозитория; резервные копии содержат личные данные. При перезапуске workers Temporal продолжает незавершённые workflows. Для внешних вызовов с неопределённым исходом повторная отправка может требовать отдельного решения: Telegram не гарантирует идемпотентную доставку сообщения при сетевом обрыве после приёма запроса.

Образы инфраструктуры закреплены в `compose.local.yaml`. Temporal auto-setup выбран по [официальному примеру Temporal](https://github.com/temporalio/docker-compose/blob/main/docker-compose-postgres.yml); это удобная среда одного сервера без TLS и отказоустойчивости. Перед публичным развёртыванием нужны отдельные сервисные учётные записи, защита endpoints и проверка обновлений образов. В MVP MinIO и приложение используют одну локальную учётную запись; пароли из примера предназначены для loopback-среды разработки.

## Ubuntu-компьютер Альберта

`docker compose -f compose.local.yaml up -d --build` собирает `computer` и запускает
одноразовый `computer-init`. Инициализатор создаёт отдельные ключи клиента и сервера.
Клиентские файлы доступны процессу OpenAlbert (UID 10001) только на чтение; на
компьютере есть лишь публичный ключ клиента и собственный ключ сервера. Приватные
ключи не входят в Git или образы. Повтор инициализации сохраняет прежние ключи.

`computer` находится в отдельной Compose-сети с приложением и имеет исходящий
интернет. PostgreSQL, Temporal, MinIO и логи в эту сеть не включены. SSH-порт не
публикуется на хосте. Сеть не является полной защитой хоста: опубликованные сервисы
и маршруты хоста требуют собственной настройки доступа. Docker socket, память и
секреты приложения в компьютер не монтируются. Внутри контейнера `albert` имеет
`sudo` без пароля; это доверенная рабочая среда владельца.

| Настройка | Значение |
| --- | --- |
| `COMPUTER_SSH_ADDRESS` | В Compose `computer:22`; явно пустое значение отключает tools. Вне Compose по умолчанию выключено. |
| `COMPUTER_SSH_USER` | `albert` |
| `COMPUTER_SSH_KEY_FILE` | По умолчанию `/data/computer/id_ed25519`; для Go на хосте задай путь к клиентскому ключу. |
| `COMPUTER_SSH_KNOWN_HOSTS_FILE` | По умолчанию `/data/computer/known_hosts`; для внешней машины нужен файл с заранее проверенным ключом и адресом сервера. |
| `COMPUTER_CPUS` | `2`, предел CPU встроенного контейнера |
| `COMPUTER_MEMORY_LIMIT` | `2g`, предел памяти встроенного контейнера |

Предел процессов — 256. Лимита общего объёма диска этот Compose не задаёт; сохраняемый
вывод каждой команды ограничен отдельно. Удаление всего `container_data/computer`
удаляет рабочие файлы, историю операций и SSH-идентичность. Сохраняй каталог вместе
с резервными копиями приложения.

Для ручного терминала владельца:

```sh
docker compose -f compose.local.yaml exec --user albert computer bash
```

Чтобы проверить адаптер на одноразовом компьютере без настоящих Telegram/LLM:

```sh
docker build -f deploy/computer/Dockerfile -t openalbert-dev:computer .
python3 deploy/computer-smoke.py
```

Проверка создаёт свои Docker volumes и контейнеры и удаляет их после запуска.
Она проверяет SSH и sudo, двоичные файлы, повтор команды без дубликата, очередь,
отмену, таймауты, лимиты вывода и сохранение данных после пересоздания компьютера.
Подробный контракт инструментов описан в [разделе удалённого компьютера](tools.md#удалённый-компьютер).

При подключении внешней машины из Compose положи отдельные `external_key` и
`external_known_hosts` в `container_data/computer/client`, с владельцем UID 10001
и правами 0600. Задай адрес и пути `/data/computer/external_key`,
`/data/computer/external_known_hosts` соответствующими переменными. Инициализатор
сохраняет эти отдельные файлы; стандартный `known_hosts` принадлежит встроенному
компьютеру и обновляется при инициализации. На внешней машине нужно разрешить
соответствующий публичный ключ и установить CLI. Проверку ключа сервера нельзя
заменять отключением host verification.
