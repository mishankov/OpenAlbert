# Приложение macOS

Нативный клиент продолжает личный разговор с Альбертом: сообщения из Telegram и
приложения видны в одной истории. В разделах доступны поручения, личная память и
файлы. Служебные сессии и внутренние вызовы модели остаются в инспекторе.

Исходники клиента находятся в `apps/macos`, контракт — в
[Desktop API v1](desktop-api.md). API использует существующие очередь входящих
сообщений, Temporal и очередь ответов; отдельный экземпляр агента не запускается.

## Подключение

На сервере задай `DESKTOP_API_TOKEN` случайным токеном длиной не менее 32 байт
и перезапусти OpenAlbert. Без этой переменной API отключён. Например, токен
можно создать командой `openssl rand -hex 32`. Передай его через используемый
менеджер секретов, не добавляя в репозиторий или URL.

В настройках приложения укажи корень HTTP- или HTTPS-адреса, например
`http://192.168.1.31:8080` для Pi в локальной сети или
`https://albert.example.com`, и токен. Токен хранится в Keychain. Один токен
первой версии даёт доступ к личному разговору владельца, заданного
`TELEGRAM_OWNER_USER_ID`; замена токена отзывает доступ у всех клиентов.
Привязки устройств с отдельным отзывом пока нет.

При HTTP-подключении токен и сообщения передаются без шифрования.
Запуск backend описан в [development.md](development.md),
сборка и проверки macOS — в `apps/macos/README.md`.
Локальный запуск и desktop-проверки выполняются в отдельной
[macOS VM](macos-development-vm.md).
Механизм обновлений и выпуск подписанных версий описаны в
[macos-updates.md](macos-updates.md).

Сквозная проверка `python3 tools/checks/check-contract.py` запускает настоящие
HTTP-обработчики Go с временными данными и прогоняет Swift-клиент через них:
авторизация, история, поручения, память, отправка, повтор, конфликт UUID,
загрузка и скачивание файла. Рабочие ключи, Telegram и модель ей не нужны.

Сообщение отправляется по Enter; Shift+Enter вставляет новую строку.
Над полем ввода отображается отправка и текущее состояние обработки с сервера.
После завершения обработки индикатор исчезает; при потере соединения
приложение показывает ошибку вместо продолжающегося индикатора.

История и состояние обработки обновляются опросом раз в две секунды. Отправка считается принятой после
сохранения в очереди, а ответ появляется после работы агента. При потере ответа
на запрос клиент повторяет отправку с тем же UUID: это не создаёт второе
сообщение. Уже загруженная история остаётся на экране при обрыве связи.

## Голосовые сообщения

Микрофон в поле сообщения начинает запись; повторное нажатие завершает её.
Перед отправкой запись можно прослушать или удалить, набранный текст остаётся
в черновике. Отправка — обычной стрелкой или Enter. Начало/конец записи —
⌘⇧R, прослушивание — ⌘⇧P, отмена — Escape. Максимальная длительность — пять
минут. Приложение запрашивает доступ к микрофону при первой записи.

Звук загружается как M4A-вложение и поступает в существующее распознавание речи
Альберта. Для распознавания на сервере нужен настроенный STT, описанный в
[speech.md](speech.md). Контракт и поведение черновика — в
[desktop-voice.md](desktop-voice.md). Сквозная проверка также кодирует настоящий
AAC-файл средствами macOS и проверяет загрузку, отправку, повтор и скачивание.

## Доступ через VPS

Схема: macOS → HTTPS на VPS с Caddy → WireGuard → Pi. На Mac WireGuard не нужен.
Шаблоны в `deploy/networking` предназначены для отдельной настройки развёртывания;
применение к рабочему серверу не входит в сборку приложения.

1. Выдели домен с DNS-записью на VPS. Открой на VPS TCP 80/443 для Caddy и UDP
   51821 для WireGuard. Создай разные ключи WireGuard на Pi и VPS и подставь их
   в `pi-albert0.conf.example` и `vps-albert0.conf.example`.
2. Используй отдельный интерфейс `albert0` и свободные адреса, в примере
   `10.77.0.1/32` на VPS и `10.77.0.2/32` на Pi. Убедись, что они не пересекаются
   с существующими маршрутами. `AllowedIPs` содержит только адрес другого узла;
   настройки default route и DNS не нужны. Caddy работает на хосте VPS и сам
   обращается к Pi, поэтому IP forwarding и NAT на VPS не требуются.
3. На Pi уже работает AmneziaWG с маршрутизацией внешнего трафика через VPN.
   До запуска нового туннеля настрой отдельный маршрут к публичному IPv4 VPS
   через обычный шлюз LAN. Для обследованной сети это маршрут `/32` через
   `192.168.1.1 dev eth0`; перед применением повторно проверь фактический шлюз,
   адрес VPS, `ip rule` и `ip route get <VPS_IP>`. Сделай маршрут постоянным
   средствами установленного сетевого менеджера. После запуска WireGuard
   проверь, что endpoint по-прежнему идёт через eth0, а `10.77.0.1` — через
   albert0. Другие публичные адреса должны сохранить прежний VPN-маршрут.
4. После появления интерфейса подключи `compose.wireguard.yaml` к основному
   Compose. Он добавляет публикацию порта только на IP нового туннеля;
   loopback-публикация для локального инспектора сохраняется. Настрой firewall
   Pi так, чтобы входящий 8080 на этом адресе принимался только от `10.77.0.1`.
   Для Docker проверяй фактические правила публикации, а не только INPUT/UFW.
5. На VPS замени домен в `Caddyfile.example`, проверь файл через
   `caddy validate --config /path/to/Caddyfile --adapter caddyfile` и загрузи его.
   Использован `handle`, сохраняющий префикс API. Все остальные пути отвечают 404.

Проверка после настройки: `/api/v1/status` без токена должен отвечать 401,
с токеном — 200. `/inspect/`, `/api/inspect/sessions`, `/healthz` через публичный
домен должны отвечать 404. Затем проверь отправку, получение ответа, скачивание
файла и переподключение после временного отключения сети. Не публикуй весь
listener OpenAlbert: старый инспектор предназначен для доверенного доступа.

Официальные справочники: [WireGuard Quick Start](https://www.wireguard.com/quickstart/)
и [маршрутизация Caddy через handle](https://caddyserver.com/docs/caddyfile/directives/handle).
