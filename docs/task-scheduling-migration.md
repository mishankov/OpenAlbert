# Слоты повторяющихся задач и maintenance

## Семантика

`next_run_at` — сохранённый ближайший слот. Длительность генерации и доставки не сдвигает фазу расписания.

- `schedule_seconds > 0`: после прогона берётся первый слот `старый next_run_at + k × schedule_seconds`, строго позже времени завершения. При простое выполняется один догоняющий прогон, остальные пропущенные слоты отбрасываются. Интервал измеряет прошедшие секунды, поэтому `86400` не означает одинаковое местное время при DST.
- `schedule_cron` + `schedule_timezone`: пять cron-полей и явная IANA-таймзона. После прогона выбирается следующий календарный слот строго после завершения. Новая задача без `next_run_at` сразу получает будущий календарный слот. Одновременное задание cron и положительного интервала запрещено.
- Сохранённый будущий `next_run_at`, в том числе выставленный текущим прогоном, имеет приоритет и не перезаписывается. Изменение конфигурации расписания сохраняет уже назначенный ближайший слот; новая конфигурация определяет последующие слоты.
- Ошибка повторяющегося прогона оставляет задачу в `waiting` со следующим слотом. Разовая задача при ошибке остаётся `failed`. Явные `paused`, `cancelled`, `completed`, `failed` по-прежнему останавливают задачу.
- Cron пропускает несуществующее местное время в весенней DST-дыре. В повторяющийся осенний час существуют два разных слота: выполняются оба, если первый прогон заканчивается до второго. Если оба пропущены, они схлопываются по общему правилу.

Для **17:00 UTC = 20:00 Europe/Moscow**:

```json
{"schedule_cron":"0 20 * * *","schedule_timezone":"Europe/Moscow","schedule_seconds":0}
```

Эквивалент в UTC: `0 17 * * *`, `UTC`. Запись `0 17 * * *`, `Europe/Moscow` означает **14:00 UTC**, а не 17:00 UTC.

## Миграция

1. Сохранить снимок `openalbert_tasks`: ID, scope, status, next_run_at, schedule_seconds, version и полное JSONB для отката. Не менять цели, результаты и промпты.
2. Заменить все старые worker-процессы новой версией до включения cron/maintenance. Сигнатуры Activities и последовательность команд Workflow не меняются: текущие Temporal-таймеры и истории сохраняются. Не перезапускать Workflow с новыми ID и не очищать outbox/checkpoints.
3. Для существующих `schedule_seconds > 0` **не выполнять UPDATE/backfill**. JSONB не требует DDL; отсутствующие новые поля имеют нулевые значения. Текущий будущий слот сохраняется, после его исполнения расчёт автоматически идёт от него. Уже накопленный сдвиг сохраняется, но больше не растёт. Просроченная активная задача выполняется один раз после восстановления, затем получает будущий слот. Приостановленные и терминальные задачи не возобновляются автоматически.
4. Для перехода на календарь обновить только поля расписания через интерактивный `task_update`, сохранив текущий `next_run_at`. Например, для превью, у которого временно убран интервал:

   ```json
   {
     "id":"b1c2f3fd8ab67501f1d57f71afc97d07",
     "schedule_seconds":0,
     "schedule_cron":"0 20 * * *",
     "schedule_timezone":"Europe/Moscow"
   }
   ```

   Если текущий слот уже равен `2026-10-27T17:00:00Z`, он останется таким. Cron делает эту задачу повторяющейся, включая следующий запуск после ошибки; ручной одноразовый якорь больше не требуется. Для остальных задач с накопленным сдвигом при необходимости отдельно назначить подтверждённый **будущий** `next_run_at`; автоматически выводить желаемое время из текста цели нельзя.
5. Выдать `maintenance:true` только выбранным сторожевым задачам через интерактивный `task_update`. По умолчанию право выключено. Сами задачи и инициативные проверки не могут его выдавать/отзывать, создавать вложенные задачи или менять другие maintenance-задачи.
6. После выкладки проверить 10 последовательных запусков: слот, старт, завершение и ровно одну успешную доставку для каждого turn ID. Старт в пределах секунды подтверждён в тестах виртуального времени; на живом сервисе он также зависит от доступности Temporal, очереди Activities и worker. Код не может гарантировать секундную задержку при их перегрузке. Доставка остаётся после генерации, а не в момент старта.

Откат: сначала остановить новые worker. Восстановить поля расписания и maintenance из снимка либо явно перевести календарные задачи в положительные интервалы с будущими слотами, затем вернуть старые worker. Старый код не понимает cron и может потерять новые JSON-поля при записи. Outbox, receipts и аудит не откатывать, чтобы не повторять доставки. Старый код вновь имеет исходный баг дрейфа.

## Права maintenance и аудит

Активная maintenance-задача может менять только `next_run_at` и `status` обычных задач в том же разговоре. Любые другие переданные поля, даже пустые, запрещены. Нельзя изменять выполняющуюся задачу, принудительно устанавливать `running`, изменять другую maintenance-задачу или назначать возобновляемой задаче слот в прошлом/настоящем. Это исключает запуск цепочек maintenance и немедленные циклы догоняющих запусков. Собственные результаты и расписание maintenance-задача сохраняет через обычное право редактировать себя.

Проверка флага и текущего статуса источника, версии и состояния цели выполняется под блокировками PostgreSQL. Изменение цели и запись `openalbert_checkpoints.id = 'task-maintenance/' + mutation_id` коммитятся одной транзакцией. Аудит содержит source/target task ID, conversation ID, run ID, mutation ID, status/next_run_at до и после, версии и время. Повтор Activity с тем же ключом не меняет задачу второй раз; параллельная устаревшая запись получает конфликт. Телеметрия `task.maintenance` связывает аудит с логами выполнения. Тексты целей и сообщений в аудит не попадают.

```sql
SELECT data
FROM openalbert_checkpoints
WHERE id LIKE 'task-maintenance/%'
ORDER BY data->>'changed_at';
```

## Проверки

```sh
task check
task test:go
```

`task check` проверяет форматирование, Go-анализ, runner, Compose и Bake. `task test:go` запускает race-тесты в Linux-контейнере с одноразовыми PostgreSQL, VictoriaLogs, Chromium и FFmpeg. Пакеты выполняются с `-p 1`, чтобы глобальное восстановление состояния хранилища одного пакета не вмешивалось в другой. Данные и контейнеры удаляются после проверки; логи сохраняются в `reports/local/`.

- `apps/backend/internal/scheduling/schedule_test.go`: 10 слотов без дрейфа, граница года/суток, пропуски, точное попадание в слот, сохранение будущих и прежних сдвинутых слотов, интервалы через DST, календарные весенний/осенний переходы, дыра в 02:30 и в полночь, оба момента повторённого часа, невалидные расписания.
- `apps/backend/internal/agent/scheduling_test.go`: явный якорь из `task_update`, идемпотентность повторного завершения, повторы после ошибки, сохранение остановки, создание/обновление cron через tools.
- `apps/backend/internal/orchestration/scheduling_test.go`: по 10 реальных Workflow-прогонов с виртуальной генерацией 143 с для cron и интервала; точный старт, точный следующий слот, отдельные turn ID, 10 HTTP-доставок и ровно один `telegram.deliver` с `delivery_state=sent` на turn; один догоняющий прогон после трёх дней простоя, включая ошибку.
- `apps/backend/internal/agent/maintenance_test.go`, `apps/backend/internal/storage/maintenance_test.go`: границы прав, запрет самовыдачи, уведомление планировщика, атомарный аудит, повторы, конфликтующие записи, запуск контракта на Memory и PostgreSQL.
